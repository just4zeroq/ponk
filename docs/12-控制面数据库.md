# 12 控制面数据库

本文档定义控制面的持久层：**选型、表结构（DDL）、与事件/存储层的边界、迁移步骤**。
覆盖五组实体——**交易所信息 / 交易所交易对信息 / 币信息 / 服务器信息 / 采集节点信息**——
外加两个派生物（订阅计划快照、节点运行时状态）与既有八域配置的版本化存储。

---

## 1. 定位与选型

### 1.1 控制面库是什么

| 是 | 不是 |
|---|---|
| **配置与目录的事实来源**（八域配置、节点定义、catalog） | 行情数据库（那是存储层的职责，04） |
| 小数据量、强事务、单实例 | 大数据量、列式分析、多实例 HA |

**与存储层的边界**：行情与信号数据在存储层（CK/duckdb）；控制面库只存**配置与目录**。
catalog 中对外可见的部分经 `md.meta` 事件送往总线 → 存储层 → 数据服务（红线 4，09 §2.4）。

### 1.2 选型：SQLite（WAL 模式）

| 项 | 取值 |
|---|---|
| 引擎 | **SQLite 3.37+，`STRICT` 表 + WAL** |
| 驱动 | `rusqlite`（`bundled` feature，自带引擎，无系统依赖） |
| 部署 | 单文件 `control.db` + `-wal`/`-shm`；备份 = 拷文件（或 `VACUUM INTO`） |
| 并发 | 单写多读；控制面是低 QPS（配置变更 + 5 分钟同步 + 5s 心跳写），WAL 足够 |

**为什么不是 PostgreSQL**：控制面 HA 已明确排除（09 §7），多实例是无需求；数据量在 MB 级。
将来真要迁 PG，本节 DDL 基本可直接复用（`STRICT`/`TEXT` 与 PG 类型一一对应）。

**为什么不是继续用文件**：配置域、快照键、计划快照需要**事务一致性**（09 §4.3 要求
"先写 meta → 同一事务写订阅集 + 递增版本 → 最后生成回填任务"），文件系统给不了；
且心跳 5s 一次的写与版本历史混在目录里会互相污染。

---

## 2. 实体关系

```
exchange ──1:N── exchange_market
                       │
                       └──1:N── instrument ──N:1── asset ──1:N── venue_asset
                                     │
                                     └──1:N── instrument_change   （变更历史）

sync_run  ─────────────────────►  instrument_change（谁触发的变更）

server ──1:N── collector_node ──1:N── node_assignment   （派生物：按版本的计划快照）
                       └────────────── node_runtime     （热：心跳 / 收敛状态）

config_domain ──1:N── config_version ──► audit_log
```

**冷热分离**是本设计的第一原则：定义与版本（冷、可回滚）与运行时状态（热、每 5s 写）**分表**，
否则高频心跳会把版本历史淹掉，也让"干净回滚"无从谈起。

---

## 3. DDL

> 约定：时间戳一律 **INTEGER（UTC 毫秒）**，与事件信封一致（03 §5.1）；
> 所方原始字段一律进 `extra`（TEXT，JSON），**不为个所怪字段加列**；
> JSON 字段用 `TEXT` 存（SQLite 的 `json_*` 函数可查）。

### 3.1 交易所与市场

```sql
CREATE TABLE exchange (
  venue            TEXT PRIMARY KEY,        -- binance / okx / bitget / hyperliquid
  name             TEXT NOT NULL,
  dig3_exchange_id TEXT NOT NULL,           -- 必须能映射到 dig3 ExchangeId，否则采集起不来
  enabled          INTEGER NOT NULL DEFAULT 1,   -- 0/1
  asset_class      TEXT NOT NULL DEFAULT 'crypto',
                                       -- crypto / stock / forex / prediction
                                       -- stock → 该所交易对跳过链上币信息（docs/14 §6）
  extra            TEXT NOT NULL DEFAULT '{}',
  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL
) STRICT;

CREATE TABLE exchange_market (
  venue             TEXT NOT NULL REFERENCES exchange(venue) ON DELETE CASCADE,
  market            TEXT NOT NULL,          -- spot / swap / future（02 §3）
  dig3_account_type TEXT NOT NULL,          -- Spot / FuturesCross …（02 §6 映射表）
  enabled           INTEGER NOT NULL DEFAULT 1,
  -- 配额份额（02 §6：按 (venue, 出口IP) 切；采集 ~50% / 回填 ~35% / 元数据 ~15%）
  quota_collect     REAL NOT NULL DEFAULT 0.50,
  quota_backfill    REAL NOT NULL DEFAULT 0.35,
  quota_metadata    REAL NOT NULL DEFAULT 0.15,
  egress_ip         TEXT,
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL,
  PRIMARY KEY (venue, market)
) STRICT;
```

> `swap → FuturesCross`（不是 `FuturesIsolated`）是 dig3 的注册键要求，见 02 §6——**写错连不上**，
> 因此 DDL 里不放默认值，由运维显式填。

### 3.2 币信息（两层）

```sql
-- 全局资产：跨所对齐的锚（BTC 只有一个）
CREATE TABLE asset (
  id         INTEGER PRIMARY KEY,
  code       TEXT NOT NULL UNIQUE,          -- BTC / USDT
  name       TEXT,
  kind       TEXT NOT NULL DEFAULT 'coin',  -- coin / token / stock / index（代币化股票等）
  -- ── 外部源（CoinGecko 为主，docs/14 §5）─────────────────────────────────
  external_id        TEXT,                 -- CG coin id（如 bitcoin）；未匹配为 NULL
  match_status       TEXT NOT NULL DEFAULT 'not_found',  -- matched / ambiguous / not_found
  twitter_url        TEXT,
  total_supply       TEXT,                 -- 十进制字符串（03 §5.5 保真）
  circulating_supply TEXT,
  detail_source      TEXT,                 -- coingecko / coinmarketcap
  detail_synced_at   INTEGER,
  extra              TEXT NOT NULL DEFAULT '{}',  -- CG 原始响应（外部源加字段不必改表）
  -- `kind` / `match_status` 可由页面改（PATCH /assets/{code}）；**不参与** instrument.row_hash
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
) STRICT;

-- 一币多链的合约地址（docs/14 §4 判断 2：**子表而非 JSON 列** —— 一对多本是关系，
-- 且"按地址反查"将来最可能用；量极小，一币 1~10 条）
CREATE TABLE IF NOT EXISTS asset_contract (
  id          INTEGER PRIMARY KEY,
  asset_id    INTEGER NOT NULL REFERENCES asset(id) ON DELETE CASCADE,
  chain       TEXT NOT NULL,                  -- TRON / Ethereum / Arbitrum ...
  address     TEXT NOT NULL,                  -- 合约地址
  standard    TEXT,                           -- TRC20 / ERC20 / BEP20 ...
  is_primary  INTEGER NOT NULL DEFAULT 0,
  source      TEXT NOT NULL DEFAULT 'coingecko',
  updated_at  INTEGER NOT NULL,
  UNIQUE(asset_id, chain, address)
) STRICT;
CREATE INDEX IF NOT EXISTS idx_contract_address ON asset_contract(address);

-- 各所口径：同一个币在不同所的精度、网络、可提可充状态都不一样
CREATE TABLE venue_asset (
  asset_id          INTEGER NOT NULL REFERENCES asset(id) ON DELETE CASCADE,
  venue             TEXT    NOT NULL REFERENCES exchange(venue) ON DELETE CASCADE,
  precision         INTEGER,
  networks          TEXT NOT NULL DEFAULT '[]',   -- ["TRC20","ERC20"]
  deposit_enabled   INTEGER,        -- 同步写 NULL（协议层 CurrencyInfo 无此字段）= 未知；供人工登记
  withdraw_enabled  INTEGER,
  status            TEXT,                          -- 所方状态字符串
  extra             TEXT NOT NULL DEFAULT '{}',
  row_hash          TEXT NOT NULL,                 -- 变更检测（§4.2）
  last_synced_at    INTEGER NOT NULL,
  PRIMARY KEY (asset_id, venue)
) STRICT;

CREATE INDEX idx_venue_asset_venue ON venue_asset(venue);
```

**为什么分两层**：`base/quote` 要能跨所对齐（信号与因子做横截面），所以全局锚不可省；
而"币安能提 TRC20、欧易 8 位精度"是各所事实，必须逐所存。这与 CCXT 的
unified currency + per-exchange CurrencyInterface 同构。

### 3.3 交易所交易对

```sql
CREATE TABLE instrument (
  venue            TEXT NOT NULL,
  market           TEXT NOT NULL,
  native_code      TEXT NOT NULL,           -- 交易所原生代码（canonical 的第三段，02 §3）
  base_asset_id    INTEGER REFERENCES asset(id),
  quote_asset_id   INTEGER REFERENCES asset(id),
  status           TEXT NOT NULL,           -- trading / break / delisted（所方口径）
  instrument_type  TEXT,                    -- spot / perpetual / future（所方原样，02 §2）
  price_precision  INTEGER,
  qty_precision    INTEGER,
  tick_size        TEXT,                    -- 十进制字符串（保真，03 §5.5）
  step_size        TEXT,
  min_notional     TEXT,
  listed_at        INTEGER,                 -- 首次见到的时间（= 上新时刻的证据）
  delisted_at      INTEGER,
  first_seen_at    INTEGER NOT NULL,
  last_synced_at   INTEGER NOT NULL,
  row_hash         TEXT NOT NULL,           -- 变更检测（§4.2）
  extra            TEXT NOT NULL DEFAULT '{}',
  PRIMARY KEY (venue, market, native_code),
  FOREIGN KEY (venue, market) REFERENCES exchange_market(venue, market) ON DELETE CASCADE
) STRICT;

CREATE INDEX idx_instrument_assets ON instrument(base_asset_id, quote_asset_id);
CREATE INDEX idx_instrument_status ON instrument(venue, market, status);
CREATE INDEX idx_instrument_synced ON instrument(last_synced_at);

-- 变更历史：审计 + "为什么重算了"的依据 + 名单决策输入
CREATE TABLE instrument_change (
  id          INTEGER PRIMARY KEY,
  venue       TEXT NOT NULL,
  market      TEXT NOT NULL,
  native_code TEXT NOT NULL,
  change_kind TEXT NOT NULL,      -- new / delisted / status / precision / type / relisted
  before_v    TEXT,               -- JSON（实际 DDL 列名；接口同时给 `before` 别名，新上时为 NULL）
  after_v     TEXT,               -- JSON（同上，接口同时给 `after`）
  detected_at INTEGER NOT NULL,
  sync_run_id INTEGER REFERENCES sync_run(id)
) STRICT;

CREATE INDEX idx_change_detected ON instrument_change(detected_at);
CREATE INDEX idx_change_instrument ON instrument_change(venue, market, native_code);
```

> **主键即 canonical**：`(venue, market, native_code)` 就是 02 §3 的 instrument 标识，
> 不再另造自增 id 给外部引用——这样库里的行、总线上的 `shard`、存储层的分区键三者同一口径。

### 3.4 同步运行记录

```sql
CREATE TABLE sync_run (
  id          INTEGER PRIMARY KEY,
  started_at  INTEGER NOT NULL,
  finished_at INTEGER,
  outcome     TEXT NOT NULL DEFAULT '{}',   -- 逐所结果：{ "binance": {"instruments":812,"changed":3}, ... }
  error       TEXT
) STRICT;
-- `outcome` 是 JSON，**同时装两种形状**（各有用途，故不拆字段）：
--   * 扁平：ran / changed / recompute_ran / diff / skipped / fetched_*  → POST /sync/runs 直回
--   * 逐所：venues: { "binance": {instruments, currencies, changed} }   → P8 轮次详情逐所展开
--   另带 summary / ts。**出错轮只写 sync_run 即返回**，catalog 事实不推进。
```

对应 09 §2.4 的 5 分钟任务：**每轮一条**，供 06 观测（哪些所拉失败了）与排障
（"这批变更是什么时候引入的" → 顺着 `sync_run_id` 查）。

### 3.4b 外部（币信息）同步运行记录

```sql
CREATE TABLE IF NOT EXISTS offchain_sync_run (
  id           INTEGER PRIMARY KEY,
  started_at   INTEGER NOT NULL,
  finished_at  INTEGER,
  outcome      TEXT NOT NULL DEFAULT '{}',  -- fetched/matched/ambiguous/not_found/detail_pulled/rate_limited
  error        TEXT
) STRICT;
```

与 `sync_run` **分离**（`docs/14 §3`）：交易所目录与外部币信息是两个节拍、两种失败语义，
混在一张表里会让"CG 限速"伪装成"交易所同步失败"。

### 3.5 服务器信息

```sql
CREATE TABLE server (
  id         INTEGER PRIMARY KEY,
  host       TEXT NOT NULL UNIQUE,          -- 机器名或 IP（与 register 上报的 host 比对）
  region     TEXT,                          -- tokyo-1 / tokyo-2 / …
  roles      TEXT NOT NULL DEFAULT '[]',    -- ["collector","storage","control","signal","alert","factor","datasvc"]
  cpu_cores  INTEGER,
  mem_gb     INTEGER,
  disk_gb    INTEGER,
  status     TEXT NOT NULL DEFAULT 'active',-- active / maintenance / retired
  labels     TEXT NOT NULL DEFAULT '{}',
  notes      TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
) STRICT;
```

**人工登记**（运维台账）。采集 register 上报的 `host` **与之关联但不强校验**：
未登记的 host 记录并告警（06），**不拒绝注册**——否则改个机器名就把采集卡死。

### 3.6 采集节点信息（定义 / 派生 / 运行时三张表）

```sql
-- 冷：节点定义（操作者输入，09 §2.3）
CREATE TABLE collector_node (
  id             INTEGER PRIMARY KEY,
  name           TEXT NOT NULL UNIQUE,      -- 唯一标识 = instance_id（10 §5 的 <instance>）
  enabled        INTEGER NOT NULL DEFAULT 1,
  server_id      INTEGER REFERENCES server(id),   -- 期望落在哪台机器（NULL = 未指定）
  -- 标的范围：规则式 + 例外清单（§5）
  scope_rules    TEXT NOT NULL,             -- {"venues":["binance","okx"],"markets":["spot","swap"],
                                            --  "channels":["candle_1m","trade"],"quote":["USDT"]}
  scope_exclude  TEXT NOT NULL DEFAULT '[]',-- 例外：排除的 native_code 列表
  scope_include  TEXT NOT NULL DEFAULT '[]',-- 例外：强制纳入（即使规则没覆盖）
  -- 运行参数（生成配置文件时写进去；不含计划本身）
  runtime_params TEXT NOT NULL DEFAULT '{}',-- publish/degrade/reconnect/heartbeat/quota 桶/capacity
  note           TEXT,
  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL
) STRICT;

-- 冷：派生物 —— 该节点的订阅计划快照（按 assignment_version 版本化，09 §5.4）
CREATE TABLE node_assignment (
  node_id            INTEGER NOT NULL REFERENCES collector_node(id) ON DELETE CASCADE,
  assignment_version INTEGER NOT NULL,
  mode               TEXT NOT NULL,         -- snapshot / diff
  plan               TEXT NOT NULL,         -- SubscribePlan JSON（03 §5.3）
  quota_splits       TEXT NOT NULL DEFAULT '{}', -- 逐所分摊（线上只带一份，完整表在此）
  generated_at       INTEGER NOT NULL,
  PRIMARY KEY (node_id, assignment_version)
) STRICT;

-- 热：运行时状态（= 快照键的持久化形态，09 §6.3）
CREATE TABLE node_runtime (
  instance_id       TEXT PRIMARY KEY,       -- = collector_node.name（同名重登 = 覆盖本行）
  node_id           INTEGER REFERENCES collector_node(id),
  host              TEXT,                   -- register 实际上报（09 §2.3 分散分片的依据）
  status            TEXT NOT NULL,          -- registered / running / stopped / dead
  applied_version   INTEGER,                -- 心跳上报（收敛判据）
  last_assignment_version INTEGER,          -- 已下发的最新版本（重登后继续递增，09 §2.3）
  counters          TEXT NOT NULL DEFAULT '{}', -- 含 capacity.* 与 cfg.<domain>
  started_at        INTEGER,
  last_seen_ts      INTEGER NOT NULL,
  lost_count        INTEGER NOT NULL DEFAULT 0,
  unconverged_since INTEGER,
  last_repush_ts    INTEGER
) STRICT;

CREATE INDEX idx_runtime_seen ON node_runtime(last_seen_ts);
CREATE INDEX idx_runtime_node ON node_runtime(node_id);
```

> `node_runtime.instance_id` 是**主键**，同名重登直接覆盖本行——这正是 02 §7.4 的语义：
> 保留 `last_assignment_version` 并继续递增，同时刷新 `host` 与 `last_seen_ts`。

### 3.7 八域配置的版本化存储

```sql
CREATE TABLE config_domain (
  domain          TEXT PRIMARY KEY,         -- 09 §2 的八域（含 instrument_blocklist）
  current_version INTEGER NOT NULL,         -- 0 = 尚未发布
  updated_at      INTEGER NOT NULL
) STRICT;

CREATE TABLE config_version (
  domain       TEXT NOT NULL REFERENCES config_domain(domain) ON DELETE CASCADE,
  version      INTEGER NOT NULL,
  content      TEXT NOT NULL,               -- 域文档本体（JSON）
  content_hash TEXT NOT NULL,               -- 审计与去重
  publisher    TEXT NOT NULL,               -- cp-1/alice
  published_at INTEGER NOT NULL,
  note         TEXT,
  PRIMARY KEY (domain, version)
) STRICT;

CREATE TABLE audit_log (
  id         INTEGER PRIMARY KEY,
  actor      TEXT NOT NULL,
  action     TEXT NOT NULL,                 -- publish / rollback / node_create / node_assign / …
  target     TEXT NOT NULL,                 -- 域或节点
  before_hash TEXT,
  after_hash  TEXT,
  detail     TEXT NOT NULL DEFAULT '{}',
  ts         INTEGER NOT NULL
) STRICT;

CREATE INDEX idx_audit_ts ON audit_log(ts);
```

**回滚 = 取历史版本内容发布为新版本号**（09 §4.5）：`config_version` 只追加不修改，
`current_version` 单向前进；回滚产生新行而非把指针倒回，收敛判据因此无歧义。

### 3.8 操作者（HTTP 面登录用户）

```sql
CREATE TABLE IF NOT EXISTS control_user (
  id            INTEGER PRIMARY KEY,
  username      TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,                 -- argon2id；**永不返回、不进日志**
  role          TEXT NOT NULL DEFAULT 'read',  -- read / write
  disabled      INTEGER NOT NULL DEFAULT 0,    -- 0/1
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
) STRICT;
```

- **用途**：`POST /auth/login` 的凭证来源；JWT 的 `sub` 取 `username`，`role` 取本表。
- **边界**：本表只服务 **HTTP 面**（`docs/13 §5.1`）；平台各节点之间**不走**它（CLI 与总线无认证面）。
- **不设防爆破字段**（`failed_attempts`/`locked_until`/`last_login_at`）：账号锁定归**反代限流**；需要时与 `jti` 吊销一并评估（`docs/13 §5.1`）。
- **引导**：**空库时自动创建内置管理员** `admin` / 默认 `admin123`（可用配置文件 `[auth].admin_password`
  覆盖），`role = write`；仅在表为空时创建一次，之后不再重建（`docs/13 §5.1` 首启引导）。
  若以 `--bootstrap none` 启动则不创建，空库登录返回 `403 no_users`。

---

**自动建行**：元数据同步必须为每个 `(venue, market)` 先建父行（`instrument`/`venue_asset` 有外键），
此时 `dig3_exchange_id` 取 `venue`、`dig3_account_type` 走 `docs/02 §6` 的映射、`extra = {"auto":"metadata-sync"}`
打上**自动创建**标记 —— 「运维显式填」由 **P3 页面复核**这些自动行，而不是让同步去等人工录入。

---

**币信息的变更历史**：`venue_asset` 有 `row_hash` 但**不设** change 表（`docs/13 §4.8` 只提供当前值
与 `last_synced_at`）。即"USDT 精度何时从 8 变 2"这类问题**查不到**——这是与 `instrument_change`
对齐时的取舍：交易对精度变化影响分片与采集，币精度只影响展示。

## 4. 与同步任务、事件、存储层的衔接

### 4.1 5 分钟同步的落库路径（09 §2.4）

```
sync_run(started_at) 建行
  → 逐 (venue, market)：拉 get_exchange_info / 币信息
  → 逐条 upsert instrument / venue_asset，比对 row_hash
      ├─ 哈希相同 → 只更新 last_synced_at（无变更零动作）
      └─ 哈希不同 → 写 instrument_change + 更新行
  → sync_run(finished_at, outcome)
  → 若有变更：触发指派重算 → node_assignment 新版本 → 经命令信道下发
  → 发 md.meta 事件（交易对 + 币信息）→ 存储层落库 → 数据服务可查
```

### 4.2 变更检测：`row_hash`

对参与变更检测的字段（不含 `last_synced_at`）按**固定顺序**规范化后取 SHA-256：

- 规范化规则与 `event_id` 的内容哈希同源（03 §5.4）：递归键排序、十进制字符串原样；
- **不含**任何时间戳与来源噪声字段，保证"内容相同 ⇒ 哈希相同"；
- 哈希变 ⇒ 写 `instrument_change`；**这是"无变更零动作"的实现基础**（避免每 5 分钟
  bump 版本、刷 `ConfigChanged`、发无意义的 `md.meta`）。

### 4.3 与事件/存储层的边界

| 数据 | 归属 |
|---|---|
| 配置与目录（本文件全部表） | 控制面库（SQLite） |
| catalog 的对外可见部分 | `md.meta` 事件 → 存储层（不当成"控制面库被外部直查"） |
| 行情/信号/因子历史 | 存储层（04），**不进控制面库** |

## 5. 采集节点的标的范围（规则式 + 例外）

**数据源分工**（A 方案）：

| 来源 | 谁维护 | 性质 |
|---|---|---|
| `instrument` / `catalog`（`venue\|market` → 标的事实） | 5 分钟同步任务（09 §2.4） | **事实**：标的是否存在、精度、状态、base/quote |
| `collector_node.scope_rules` | 操作者 | **意图**：我要哪些所 / 市场 / 计价币 / 状态 / 通道 |
| `collector_node.scope_include/exclude` | 操作者 | **例外**：规则表达不了的精确条目 |
| `SubscribePlanDoc.instruments`（逐条） | 操作者 | **手工池**：与规则解析结果合并后进指派（不废弃，但不再是主路径） |

解析器：`crates/control/src/scope.rs::resolve(scope, include, exclude, catalog) -> ScopeOutcome`
（`instruments` 入选 + `unresolved` 未能解析的例外条目及原因）。

* `include`/`exclude` 支持 **canonical**（`venue:market:native_code`，精确到所）与
  **裸码**（`BTCUSDT`，跨所生效）两种写法；
* **catalog 查不到的例外条目不臆造精度**，进 `unresolved` 并如实汇报（不静默丢）；
* **黑名单不在解析阶段**——统一在指派阶段剔除（优先级最高），因此 `include` 也拉不回它。



`collector_node.scope_rules` 是**声明式选择规则**，不是逐条标的列表：

```json
{
  "venues":   ["binance", "okx"],
  "markets":  ["spot", "swap"],
  "channels": ["candle_1m", "trade", "ticker", "l1", "funding"],
  "quote":    ["USDT"],
  "base_exclude": ["USDC", "TUSD"],
  "status":   ["trading"]
}
```

解析顺序（指派时执行，结果落 `node_assignment.plan`）：

```
候选标的 = instrument ⋈ (venues, markets, quote, status)
         − scope_exclude（例外排除）
         − InstrumentBlocklist 域（黑名单，09 §2 独立域）
         + scope_include（例外强制纳入；仍受黑名单约束）
         → 按 owner 归组 → 组内切分片 → 归属放置 → SubscribePlan
```

**分桶服从 owner 归组（模型 1 的落地方式）**：

1. 先为每个标的确定 **owner** = 第一个允许持有它的候选实例
   （无节点定义的实例视为不限制；**声明了范围但解析出 0 条 → 拒绝全部**——
   否则写错的 scope 会静默采全市场）；
2. 再按 `(venue, market, owner)` 分组、组内按 `shard_size` 切桶；
3. 放置阶段只有 owner 本人可持有该桶，非 owner 报 **"scope 未覆盖"**
   （与"承载不足"区分，便于定位是范围问题还是容量问题）；
4. 无人允许的标的落到哨兵 owner，同样报 scope 原因，**不静默丢弃**。

> 顺序不能反过来（先按 venue/market 哈希切桶、再整桶过滤）：桶里只要混进一个范围外标的，
> 整桶就无人可接——运营者声明了标的却一个也采不到，且是静默的。

**为什么规则式**：全市场是常态（一个所能有上千标的），逐条列既写不出也维护不了；
但存在"只采某几个标的"的场景，所以保留 `scope_include/exclude` 作为例外通道。
**黑名单优先级最高**：`scope_include` 也不能把黑名单标的拉回来。

## 6. 迁移步骤（从现有文件型实现）

现有实现：`store_root/config/<domain>/…`（域版本）、`store_root/state/keys/*.json`（快照键）、
`store_root/state/plans/<instance>/vN.json`（计划快照）。

| 步 | 动作 | 幂等性 |
|---|---|---|
| 1 | 建库并跑本文件 DDL（`PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON;`） | 幂等（`CREATE TABLE IF NOT EXISTS`） |
| 2 | 导入域版本：`config_version` 按 `(domain, version)` 插入，`config_domain.current_version` 取目录里的最新 | 幂等（主键冲突跳过） |
| 3 | 导入快照键 → `node_runtime`；导入计划快照 → `node_assignment` | 幂等（覆盖写） |
| 4 | **影子双写**：一段时间内文件与库同时写，比对一致性 | — |
| 5 | 切换：**库为唯一事实来源**，文件退化为**导出**（`ponk-control export --node X` → TOML，02 §7.3） | — |
| 6 | 校验：导出结果与切换前文件逐字节比对（同一版本） | — |

**回退**：第 5 步之前随时可退回文件（库只是影子）；第 5 步之后回退需反向导出，
因此切换前必须完成第 4 步比对。
