# 06 监控告警（Monitoring & Alerting）

> 对应 `01-architecture` §4.5（O1~O4）。监控告警模块主职 = **对信号规则告警**；副职 =
> 平台性能监控。渠道后端可插拔（飞书/钉钉一期；电话/短信/邮件二期）。

---

## 1. 定位与边界

```
① 事件中心 ──► signal.* ──► ④ 监控告警(独立进程)
              ├─► ops.*  ──►    │  告警规则配置(来自控制面 M2)
              │                 │  条件判定 → 路由 → 去重/节流/聚合/升级
              │                 ▼
              │              告警事件(alarm.*) ──► ① 事件中心 ──► 落库(04)
              │                             └──► 渠道后端(可插拔):
              │                                   飞书/钉钉(一期)
              │                                   电话/短信/邮件/自定义Webhook(二期)
```

- **主职：信号规则告警**——消费 `signal.*`，按**独立告警规则配置**判定并推送。
- **副职：平台性能监控**——消费各进程上报的 `ops.*` 心跳/指标，检测延迟/断流/落后/畸形。

## 2. 告警规则（独立配置，B 模式）

信号引擎只产信号（不含渠道），告警是独立配置（`alert rules`）：

```yaml
alerts:
  - name: BTC-4h-rsi-overbought
    match:
      signal_id: "btc_4h_momentum"     # 只对该信号
      # 或按 signal 族 / instrument / direction / version 过滤
    when:
      - field: rsi                    # 引用信号事件 payload 字段
        op: ">"
        value: 70
      - all: [ ... ]                  # AND/OR
    window:
      occurrences: 2                  # 时间窗内 N 次
      within: "10m"
    route:
      - channel: feishu              # 渠道后端
        target: "feishu_default"     # 渠道 id；凭据与 webhook 收敛在 Channels 域（09 §3.4）
      - channel: phone_sms           # 二期
        target: "oncall_phone"       # 渠道 id（09 §3.4）
    throttle: "5m"                    # 节流/去重
```

- 规则配置存**控制面**（M2），引擎拉取 + `ctl.config.changed` 热更新。
- 告警规则引用的是**信号事件 payload 字段**——所以信号事件必须带因子值明细（05 §4），
  否则告警条件没东西可判。

## 3. 渠道后端（可插拔 trait）

- **一期**：飞书 / 钉钉（Webhook，免费、国内主力）。
- **二期**：电话 / 短信（付费、需出站鉴权+计费）/ 邮件 / 自定义 Webhook。
- 渠道后端 trait：`notify(route, alarm_event, context)` —— 与事件中心/存储层的「契约+能力」同款
  套路，渠道差异（重试/鉴权/限额）在适配器内部消化。

## 4. 告警事件（结构见 03 §5.3，本节只述语义）

**结构定义集中在事件中心协议层**（`AlarmEvent`，03 §5.3），各组件共享。

| 字段 | 语义 |
|---|---|
| `alarm_id` | **告警实例 ID = 幂等键**（同规则同触发源去重 + 节流）——防渠道被打爆 |
| `rule_id` | 触发它的告警规则 |
| `signal_id` | 若由信号触发，回指该信号 |
| `level` | Info / Warn / Critical —— 决定默认路由与升级 |
| `title` / `detail` | 人读标题 + 结构化上下文（渠道模板渲染用） |
| `triggered_ts` | 触发时间（ms） |

- 告警事件**不携带 venue / market / native_code / exchange_ts**（03 §5.1 两级信封）：
  平台级告警（心跳丢失、总线积压）本就没有交易所与标的语义；由信号触发的告警通过
  `signal_id` 回指信号，需要标的时由信号事件提供，不在信封里冗余一份。
- 告警事件回流 `alarm.*` → 落存储层（04 扩展 alarm 表）→ **告警历史可查、可回放**。
- `alarm_id` 幂等避免重复推送（03 §5.4 幂等键语义）。
- `AlarmEvent` **无版本字段**：规则版本写入 `detail["rule_version"]`（不改协议）。

## 5. 平台性能监控（副职，O2）

- **两路观测**：
  - `ops.*`（进程自己上报）：心跳 / `applied_version` / 发送积压 / 降级计数 / 消费落后(Lag)。
  - **`md.*` 流本身**（06 自己订阅）：延迟 = `received_ts - exchange_ts`、**断流/静默按通道统计**、
    ⚠️ **K 线族的该值是「bar 起点 → 收到」**（`exchange_ts` = `open_time`，03 §5.1），不是端到端延迟；
    畸形率。**采集不报静默**（采集无状态，02 §4），断流判定从数据流直接得出。
- 告警引擎对两路做统计 → 平台级告警（如「binance spot kline 断流 60s」「信号引擎心跳丢失」
  「总线积压 > N」）。
- **断流判定用通道级 + 连接级信号**，不靠单标的静默（冷门标的凉很久不误报，沿既有 PONK 决策；
  ticker 是周期全市场推送，通道级静默即可判）。
