# 14 目录类页面与币信息（交易所 / 交易对 / 币）

本文档覆盖三个目录类页面与其后端数据链：**交易所与市场（P3）、交易对（P4/P4b）、币信息（P5）**，
以及币信息的**外部数据源**（CoinGecko）与**匹配策略**。

---

## 1. 定位与边界：一条硬规则

> **catalog 是全量目录**（`instrument` / `asset` **不因黑白名单、节点 `scope_rules`、订阅计划被剔除**）；
> **名单只作用于采集范围**（`InstrumentBlocklist` / 节点 scope → 决定"要不要订阅这条 `md.*`"）。

推论：

| 问题 | 结论 |
|---|---|
| 黑名单标的在 `instrument` 表里吗 | **在**。黑名单在**指派阶段**剔除（`assign::index_blocklist`），不在 catalog 解析阶段 |
| 节点 scope 影响 catalog 吗 | **不影响**。`scope_rules` 只决定该节点采什么 |
| 页面能增删交易对/币吗 | **不能**（只读）。同步是唯一写入方；排除某标的走**黑名单配置域**（P6） |
| 交易所与市场能改吗 | **能**（人工台账：建/改/启停/配额），它是"我方选择"而非"所方事实" |
| 股票类交易对 | 只同步交易对信息，**跳过链上币信息**（§6） |

**单写入方**是这里的核心约束：交易对/币由同步按 `row_hash` 比对写入，若页面也能改，
下一轮同步会按所方返回把人工改动冲掉（哈希不同即覆盖）——表现为"改了 5 分钟自己变回去"，
且 `row_hash` 无法区分"我改的"与"所方改的"。

---

## 2. 三类事实源

| 数据 | 来源 | 写入方 | 频率 |
|---|---|---|---|
| 交易所 / 市场 | **人工台账**（`dig3_exchange_id`、`dig3_account_type`、配额、出口 IP 显式填） | 页面（P3） | 人工变更时 |
| 交易对 `instrument` | dig3 `get_exchange_info(AccountType)` | **交易所同步任务** | **5 分钟** |
| 币：全局 `asset` 行 | 由交易对的 `base`/`quote` 派生（代码、`kind`、`name`） | **交易所同步是唯一写入方**；CG **只补空**（`name` 为空时），不覆盖 | 随交易对同步 |
| 币：各所 `venue_asset` | 交易所币信息端点（**按所可选，未接即跳过**） | 交易所同步任务 | 随交易对同步 |
| 币：链/合约/Twitter/发行流通 | **CoinGecko**（主源，§5） | **外部同步任务（独立节拍）** | 1 小时节量 + 详情轮转 |

**同步目标 = `exchange_market` 中 `enabled=1` 的 (venue, market)** —— 不是 `SubscribePlan` 域。
理由：`SubscribePlan` 是"采集意图"（派生自节点 scope，冷启动为空 → 会造成"先有鸡还是先有蛋"的死锁），
而 `exchange_market` 是"接入台账"。**目录同步要回答的是"这个所有什么标的"，不是"我要采什么"**。

**全量的粒度是标的，不是交易所**：已接入的所，它的标的一个不漏（不受名单影响）；
“接哪些所”仍由操作者在 P3 登记，**`exchange.enabled` 与 `exchange_market.enabled` 必须两侧都为 1 才同步**
（关掉所即停止同步它的全部市场，关掉单个市场只停该市场）。

## 3. 两个同步任务（节拍分离）

| | 交易所同步 | 外部（币）同步 |
|---|---|---|
| 节拍 | **5 分钟**（`META_SYNC_INTERVAL_MS`） | **1 小时**（`OFFCHAIN_SYNC_INTERVAL_MS`） |
| 目标 | `exchange` **与** `exchange_market` **两侧 `enabled=1`** 的 (venue, market) | catalog 中**全部去重的币（base ∪ quote）** |
| 记录 | `sync_run`（每轮一条） | **`offchain_sync_run`**（每轮一条，独立表） |
| 防重入 | `is_running` 单飞 | 同 |
| 手动触发 | `POST /sync/runs`（已实现） | `POST /sync/offchain/runs` |
| 失败隔离 | 各自记录，互不影响 | CG 限速/失败**不得**伪装成交易所同步失败 |

**为什么分离**：交易所目录是"事实必须新鲜"（影响采集与黑名单判定），币的供应量/社交信息是"参考数据"，
时效性差两个数量级；绑在同一轮里，要么 CG 拖慢目录同步，要么 CG 失败污染 `sync_run` 的语义。

**币信息的字段分层**（决定请求量）：

| 字段 | 变化速度 | 策略 |
|---|---|---|
| 排名、发行量、流通量（列表要显示） | 慢变 | **每轮**拉 `/coins/markets`（分页 250/页 → 4~6 请求，覆盖全部） |
| 链、合约地址、Twitter、主页 | **几乎不变** | **首次出现时拉一次**（`/coins/{id}`）+ **低频轮转**（每轮 `coin_detail_batch = 20` 个；**全量周期 = 去重币数 ÷ batch**，1500 币 / 20 ≈ 两周，不要写死"一周"） |
| **拉取失败** | — | 本轮内最多重试 `coin_detail_max_retries` 次；**失败也推进 `detail_synced_at`**，让它退到轮转队尾——否则一个永久失败的币会堵死整条队列（头阻塞）；事实记进 `outcome.detail_failed` + `error` |
| 股票类交易对 | 不适用 | **完全跳过**（§6） |

**速率账**（CoinGecko 免费档 30 req/min，无需 key）：逐币详情全量 ≈ 900 次 ≈ **30 分钟**——
所以**不能每轮全量拉详情**；轻量列表 4~6 请求/轮则毫无压力。

## 4. 表结构变更（**DDL 以 `docs/12` 为准**，本节只述语义）

| 变更 | 位置 | 语义 |
|---|---|---|
| `exchange.asset_class` | `docs/12 §3.1` | `crypto`/`stock`/`forex`/`prediction`；`stock` → 该所交易对**跳过链上币信息** |
| `asset` **新增 8 列**（`kind` 是既有列，不计） | `docs/12 §3.2` | `external_id`、`match_status`、`twitter_url`、`total_supply`、`circulating_supply`、`detail_source`、`detail_synced_at`、`extra` |
| `asset_contract` 新表 | `docs/12 §3.2.1` | 一币多链的合约地址（子表，非 JSON 列） |
| `offchain_sync_run` 新表 | `docs/12 §3.4` | 外部同步每轮一条，与 `sync_run` 分离 |

**三条设计判断**（理由在此，DDL 在 12）：

1. **`asset_class` 用人工台账而非自动判定**：按 symbol 外观猜会误伤（`BTC`/`ETH` 也是纯字母）；
   按"CG 拉不到"判又会把数据缺失误当资产类别。填错的兜底 = 页面改单个 `asset.kind`。
2. **`asset_contract` 用子表而非 JSON 列**：一对多本是关系；**按地址反查**将来最可能用，
   子表走索引；量极小（一币 1~10 条）。`extra` JSON 只承接**原始/次要**字段，
   **结构化且要被引用的字段一律建列建表**（与 `instrument.extra` 同一惯例）。
3. **`is_primary` 选法**：同币多链时按 `chain` 字典序取第一条为主链（数据源不给优先级；
   每次写入统一刷新，保证同一批次内唯一）。`standard`（TRC20/ERC20）**数据源不提供，恒为 NULL**，
   列先建好，将来源能给再填。
4. **`kind` 与 `match_status` 都可由页面改**：前者是人工兜底，后者在人工指定
   `external_id` 后由服务端置为 `matched`。二者**不参与**交易对的 `row_hash` 比对。

## 5. 外部数据源

### 5.1 选型：CoinGecko 主源，CoinMarketCap 备选

| | CoinGecko（**主**） | CoinMarketCap |
|---|---|---|
| 起步 | **Demo 档无需 API key**（30 req/min） | 需注册 API key（免费档有月度额度） |
| 链 + 合约地址 | `/coins/{id}` 的 `platforms` → `{chain: address}` | `/cryptocurrency/info` 的 `contract_address` |
| Twitter | `links.twitter_screen_name` | `urls.twitter` |
| 发行 / 流通 | `total_supply` / `circulating_supply` | 同 |
| 覆盖 | 更广（小币、部分 RWA） | 主流更全 |

抽象为 `OffchainProvider` trait + 两个适配器，`control.toml [providers] coin = "coingecko" | "coinmarketcap"` 切换；
**密钥按既有规则放配置文件**（`[providers]`，不进八域）。

### 5.2 匹配策略：三级，宁可"未收录"不静默错配

| 情况 | 处理 |
|---|---|
| `symbol` 大小写不敏感**精确唯一**命中 | 自动 `external_id = <cg_id>`，`match_status = 'matched'` |
| **多命中**（同 symbol 多个项目） | **不自动选**，`match_status = 'ambiguous'`，页面列候选由人点选 |
| **零命中**（含股票、缩放前缀如 `1000PEPE`） | `external_id = NULL`，`match_status = 'not_found'`，页面显示"未收录"，**允许手填 CG id** |

**不做**模糊匹配与"剥数字前缀"的归一化规则——`1INCH` 会被误伤，且错配会**静默污染**
（把 A 币的供应量贴到 B 币上，页面看起来"有数据"却无从察觉）。将来若需支持缩放前缀，
用**显式别名**（改 `external_id`），可审计。

索引来源：`/coins/markets` 分页拉全量 `id/symbol/name` 建索引（4~6 请求一次）；
多命中时的候选**不落库**（避免脏表）。
**一期不提供候选查询端点**：`ambiguous` / `not_found` 一律由操作者**手输 CG id**
（页面做 `[A-Za-z0-9._-]` 校验），避免每查一次候选就打一次外部 API；候选点选列表属二期。

## 6. 交易所与市场页（P3）—— 唯一可写页

**创建交互：两步**（方案 A）——

1. 「新建交易所」表单：`venue` / `name` / `dig3_exchange_id` / `enabled` / **`asset_class`**
   （§4，默认 `crypto`）/ **`extra{}`**（可选 JSON） → `POST /exchanges`
2. 展开行 / 详情页内逐个建市场：`market` / `dig3_account_type` / **配额三项** / `egress_ip`
   → `POST /exchanges/{v}/markets`

**为什么两步**：配额与出口 IP 是**每市场独立**的（现货与永续限频本就不同，`02 §6` 的
0.50/0.35/0.15 按所×市场计算），合并表单需要嵌套子表单；且市场可后加（新建 `swap` 不必重编辑整所）。

**列表页不显示"平均配额"**（无物理意义）——显示**市场数**，配额摘要在展开区按市场逐条列出。

其它操作：编辑（`If-Match` / ETag，`412`/`428` 语义）、`PATCH .../enabled` 启停、
删除（有关联市场时需 `?confirm=<venue>`，返回 `400 + detail.confirm`）。

## 7. 交易对页（P4）与币信息页（P5）

### 7.1 形态规则（全局）

**管理用页面、浏览用抽屉**：
- 管理场景（可写、有表单、要 ETag、跨页跳转）→ 子路由详情页（如 `/nodes/:name`）
- 浏览场景（只读、筛选为主）→ **行点击右侧抽屉**，列表的筛选与滚动状态不丢

交易对与币都是浏览型 → **抽屉**；交易所页用**展开行**（列表+展开市场，与其"台账"性质相符）。

### 7.2 交易对页（只读）

- **筛选**：`venue` / `market` / `status` / `native_code` 模糊 / `base` / `quote` / `synced_after`
- **列**：venue、market、native_code、base/quote、status、价格精度、数量精度、`tick_size`/`step_size`（**十进制字符串**，03 §5.5）、`last_synced_at`、**「历史」链接**
  > `GET /instruments` 的行**不含变更指示字段**，逐行再查 `changes` 会变成 N+1——故列上不放
  > 变更图标，改为点开抽屉后看**变更历史区块**（一次请求）。
- **抽屉两个区块**：标的详情（含 `extra` 原始 JSON）+ **变更历史**（`before_v/after_v`、时间倒序、按 `change_kind` 筛）
- **导出**：CSV（`/instruments/export`）
- **base / quote 可点** → 跳币信息页（交叉跳转）
- **排除某标的**：跳转到黑名单配置域（P6）——本页**不提供写入口**

### 7.3 币信息页（两 Tab）

| Tab | 数据 | 字段 |
|---|---|---|
| **全局资产** | `asset`（一币一行，去重） | code、name、kind、**匹配状态**（`matched`/`ambiguous`/`not_found` + 手填 `external_id`）、Twitter、发行量、流通量、来源、`detail_synced_at` |
| **各所口径** | `venue_asset`（一币×一所） | venue、precision、networks、可提/可充、所方 status、`row_hash`/`last_synced_at` |

- **详情抽屉**：`asset_contract` 子表（链/地址/标准/主链）+ CG 原始 `extra` + **"在交易对中查看"**（跳 P4 按 base 预筛）
- **手动同步**：头部「立即同步币信息」→ `POST /sync/offchain/runs`，旁显 `detail_synced_at` 与上轮结果
- **可写点**：`PATCH /assets/{code}`（`kind` / `external_id`）——即 Q3-D 的人工兜底与 Q6 的手填覆盖

### 7.4 空态与手动触发（**按页面各自的数据来源**，不做统一文案）

原设计要求"三页对称、都写每 5 分钟"，**与 §2 冲突**：交易所与市场是**人工台账**（同步填不出
交易所行），全局 `asset` 行**由交易对同步派生**（外部币同步只补详情字段）。因此空态按页区分：

| 页面 | 空态文案 | 主按钮 | 副按钮 |
|---|---|---|---|
| **P3 交易所** | 「尚无数据 —— 交易所与市场是**人工台账**（§2），需本页登记」 | **新建交易所（第一步）** | 「立即同步交易对」（`POST /sync/runs`） |
| **P4 交易对** | 「尚无数据 —— 交易对**每 5 分钟**自动同步一次，可立即触发」 | 立即同步（`POST /sync/runs`） | — |
| **P5 币信息** | 「尚无数据 —— 全局资产由**交易对 base/quote 派生**；链/合约/Twitter/发行流通由**外部源每 1 小时**同步」 | 立即同步币信息（`POST /sync/offchain/runs`） | 「先同步交易所目录」（`POST /sync/runs`）——否则外部同步无输入 |

**判定规则（三页通用）**：

- **同步进行中**显示 `running`：`sync_run` / `offchain_sync_run` 的 `started_at` 有值而 `finished_at`
  为空；触发后轮询，**只有 `finished_at` 落库才显示"已完成"**；超时如实报"可能仍在后台运行"
- **状态端点不可用** → 黄色告警显示原因，**不显示假轮次**
- **筛选无结果**用单独文案（"当前筛选条件下无结果 + 清除筛选"），**不冒充"尚无数据"**

## 8. 配置（`control.toml [providers]`，新增段）

```toml
[providers]
coin = "coingecko"                  # coingecko | coinmarketcap
# coin_api_key = "..."              # 可选：CG Demo 档无需；CMC 必填
offchain_interval = "1h"            # 外部同步节拍
coin_market_page_size = 250         # /coins/markets 分页大小
coin_detail_batch = 20              # 每轮轮转拉取的详情币数（≈900/20 ≈ 一周扫完）
coin_detail_max_retries = 2
coin_timeout_ms = 10000             # 外部（CoinGecko）单次请求超时

# ── 交易所取数（09 §2.4：统一经 dig3 连接器层）────────────────────────────
exchange_timeout_ms = 10000         # 覆盖 dig3 内置的 30s —— 否则一轮会打满 150s
exchange_cooldown_ms = 60000        # 连接失败的 base 在此时长内不再重试

# base 候选表：键 = "<venue>.<market>"，另有 "<venue>.currencies"（币信息）
# **值只到 origin，不含 path/query** —— 路径由 dig3 的端点定义自己拼；
# 按序 failover，首个成功的胜出；未列出的键沿用内置默认，键缺失 = 未核对端点。
[providers.dig3_rest_base]
"binance.spot" = ["https://data-api.binance.vision", "https://api.binance.com"]
"binance.swap" = ["https://fapi.binance.com"]
"okx.spot"     = ["https://www.okx.com"]
"okx.swap"     = ["https://www.okx.com"]
"okx.currencies" = ["https://www.okx.com"]   # Binance 不给键 → 如实 unsupported
```

**不进八域**：与密钥同一处理（`03`/`13` §5.1 的口径）——它们是连接凭据与调优参数，不是平台配置。

**为什么按 `(venue, market)` 而不是按 venue 配 base**：dig3 的 `rest_override` 是
per-`ExchangeId` 的**单值**，而 Binance 的现货与永续本就是两台主机（`api.` vs `fapi.`），
一个 override 会把两者一起改写（其 `assemble_rest_url` 的 prefix 模式会丢弃 `real_base`）。
控制面给每个 `(venue, market)` 各建一个 `ExchangeHub` 实例，粒度问题在本仓解决，
**dig3 的 plumbing 不用动**。这也让镜像/代理只影响它该影响的那个市场。

## 9. 接口增补

| 方法 | 路径 | 说明 |
|---|---|---|
| PATCH | `/assets/{code}` | 改 `kind` / `external_id`（手填 CG id 后服务端置 `match_status = matched`）；`If-Match` |
| GET | `/assets/{code}/contracts` | 链 + 合约地址列表（子表）；详情抽屉用 |
| POST | `/sync/offchain/runs` | 立即触发外部同步（202，复用 forced 模式） |
| GET | `/sync/offchain/status` | 上一轮 `offchain_sync_run` 结果（含 `rate_limited` / 失败原因） |

**响应形状**（前后端按此实现，`docs/13 §4.1` 的分页规则同样适用）：

- `GET /assets/{code}/contracts` → **裸数组**（该端点未列 `limit`，故不分页）：
  `[{"chain","address","standard","is_primary","source","updated_at"}]`；**无记录返回 `[]`**
  （资产存在但暂无合约信息是合法状态，不是 404）
- `GET /sync/offchain/status` →
  `{"running": bool, "last_run": {id, started_at, finished_at, outcome{}, error} | null, "detail_synced_at": <ms|null>}`
  —— `last_run` 无记录时为 **`null`**（不是空对象）
- `POST /sync/offchain/runs` → **202**：`{"ran": true, "offchain_run_id", "outcome": {...}, "error": null, "ts"}`
  （与现有 `POST /sync/runs` 的 `{ran, …, sync_run_id, …, ts}` 同构）
- `PATCH /assets/{code}` → `200` + 更新后的 `AssetRecord`；传 `external_id` → 服务端置
  `match_status = matched`；传 `null` → 清空并退回 `not_found`（允许撤销手填）；
  `kind` / `external_id` **不参与** `instrument.row_hash`

**已有、直接复用**：`/exchanges*`（CRUD + 启停 + markets）、`/instruments*`（列表/详情/导出/变更）、
`/assets`（列表/详情/各所层/导出）、`POST /sync/runs`、`GET /sync/status`。

**能力状态翻转**：`capabilities.ts` 中 `exchanges` / `instruments` / `assets` 由 `not_wired` → `ready`；
路由的 `NotWiredView` 换成真实视图。

## 10. 实现事项（分阶段）

1. **DDL**：`exchange.asset_class`、`asset` 八列、`asset_contract`、`offchain_sync_run`（幂等迁移 + `ensure_columns`）
2. **配置**：`control.toml [providers]` 解析（并入现有 `FileConfig`）
3. **外部同步**：`OffchainProvider` trait + CoinGecko 适配器（市场列表分页、详情按需与轮转）、匹配三级逻辑、`offchain_sync_run` 落库、`asset_contract` upsert
4. **接口**：§9 四条新增 + `asset` 写路径的 `match_status` 规则
5. **前端**：三页视图（P3 展开行 CRUD、P4 抽屉+变更、P5 双 Tab+抽屉）、空态与手动同步、交叉跳转、能力状态翻转
6. **测试**：全部**离线**（`OffchainProvider` 用注入的假实现：多命中、零命中、限速、部分失败）；现有测试不破
7. **联调**：三页在真实 `serve --http` 下跑通（建所 → 同步 → 有数据 → 看变更 → 看币详情）

## 11. 已知风险

| 风险 | 说明与缓解 |
|---|---|
| CG 免费档限速 | 30 req/min；轻量列表每轮 4~6 请求无压力；详情靠"首次 + 轮转"摊开；`rate_limited` 记进 `offchain_sync_run` 并在页面展示 |
| 匹配错配 | 只做精确匹配 + 人工覆盖，**宁可 `not_found`**（§5.2） |
| CG 无该币（小币/股票） | `not_found` + 页面可手填；股票类按 `exchange.asset_class` 直接跳过 |
| 交易所未提供币端点 | `venue_asset` 允许为空（该所层显示"未提供"），**不阻塞**交易对同步（币信息失败单独记录） |
| 外部源不可用（网络/停服） | 独立节拍 + 独立记录，**不影响**交易所同步；页面显示上轮失败原因 |
| 人工与同步冲突 | 交易对/币只读；可写仅 `asset.kind`/`external_id`，且不参与 `row_hash` 比对（不入库到比对字段） |
