# 09 控制面（Control Plane）

> 对应 `01-architecture` §4.8（M1~M3）。控制面是全平台**配置的事实来源**：信号规则、告警规则、
> 因子规则、订阅计划、渠道配置、进程承载参数、序列化格式、交易对黑名单八个配置域集中存放、
> 独立版本化、可审计可回滚；事件中心只承担「配置已变更」通知与拉取应答，配置本体由控制面提供
> （M1/M2）。结构定义集中在事件中心协议层（03 §5.3），本文件只述配置域、语义、流程与示例。
> 部署形式与编排不纳入设计（M3）。

---

## 1. 定位与边界

```
   操作者 / 自动化 ──写接口──► ⑨ 控制面（配置事实来源 + 指派器 + 状态观测面）
                                  │ ① ConfigChanged → ctl.<domain>        (通知)
                                  │ ③ ConfigSnapshot / SubscribePlan      (应答)
                                  │    → ctl.<node_kind>.<instance>
                                  │ ② ctl.request.<instance>               (拉取, 上行)
                                  ▼
                            ① 事件中心 ──► ②存储 ③信号 ④告警 ⑤因子 ⑥数据服务
                                  │
                                  └── ops.<node_kind>.<instance>           (状态, 上行)
```

| # | 定位 |
|---|---|
| P1 | **配置的事实来源**（M1/红线 3）：八个配置域的唯一权威存储；各节点本地只持有「拉取到的快照 + 版本」，不产生本地配置事实 |
| P2 | **星型拓扑中的一个节点**（红线 4）：与其余节点不直连，一切交互经事件中心；配置拉取也是总线消息（`ctl.request.<instance>`），不设第二条传输 |
| P3 | **双向、单一传输**：下行 = 变更通知 + 拉取应答；上行 = 拉取请求 + `ops.*` 状态。控制面不代发告警、不代发他节点的心跳（10 §5） |
| P4 | **不涉及部署编排**（M3）：进程数量、起停、宿主、拓扑均为平台使用者的事务，本文档不含任何部署内容 |
| P5 | **不做配置协商、不做应用失败反馈**（§7）：格式与 schema 由控制面单方下发，实例侧的失败只以「版本不收敛」可见 |

**引导配置例外**：事件中心地址、控制面应答主题寻址、`instance_id` 由进程启动参数注入，不属配置域。
红线 3 约束的是平台业务配置，启动引导参数不属于其范围。

控制面同时是两个面：

| 面 | 输入 | 输出 |
|---|---|---|
| **配置写入面** | 操作者/自动化提交的域文档变更 | 版本历史、审计条目、`ConfigChanged` |
| **状态观测面** | `ops.<node_kind>.<instance>`（消费组） | 快照键、收敛比对、`ops.control` 心跳 |

## 2. 配置域全集

八个域，域即**版本单位**：一域一文档（文档内含多条规则），发布即该域版本 +1。

| `ConfigDomain` | 配置域 | 消费者 | 变更如何传播 | 版本字段 |
|---|---|---|---|---|
| `SubscribePlan` | **订阅计划**：标的候选集（白名单）、通道集、分片参数、instrument meta、配额份额 | 02 采集（唯一外部消费者）；控制面指派器（派生输入） | ① 广播 `ctl.subscribe_plan` 通知 ② 定向推 `ctl.collector.<instance>` 交付 `SubscribePlan` ③ 拉取 `ctl.request.<instance>` 应答 `SubscribePlan` | 域版本 u64（文档内容）+ `SubscribePlan.assignment_version`（实例级命令序号，10 §4.3） |
| `SignalRules` | **信号规则**：RuleGraph DAG、算子参数、作用标的、输出映射（05 §2） | 05 信号引擎 | 广播通知 → 拉取应答 `ConfigSnapshot` | 域版本 u64；信号事件 `SignalEvent.version = v<域版本>` |
| `AlertRules` | **告警规则**：match / when / window / level / route / throttle（06 §2） | 06 监控告警 | 广播通知 → 拉取应答 `ConfigSnapshot` | 域版本 u64；`AlarmEvent.rule_id` 稳定，规则版本写入 `AlarmEvent.detail["rule_version"]`（不改协议结构） |
| `FactorRules` | **因子规则**：输入通道、窗口、计算算子、输出因子（07 §4） | 07 因子挖掘 | 广播通知 → 拉取应答 `ConfigSnapshot` | 域版本 u64；因子事件 `FactorEvent.version = v<域版本>` |
| `Channels` | **渠道配置**：飞书/钉钉 backend、endpoint 与凭据、重试与限额（06 §3） | 06 监控告警（路由目的地） | 广播通知 → 拉取应答 `ConfigSnapshot` | 域版本 u64；告警事件不带版本，路由时读实例当前快照 |
| `ProcessCapacity` | **进程承载上限与指派参数**：每进程最大分片数/标的数/通道数、分布策略、**按 host 分散策略** | 控制面指派器（**无外部消费者**，见 §5.2） | 不发通知（消费者在控制面内）；变更触发指派重算，效果以 `assignment_version` 落到采集 | 域版本 u64；外部可见的只有重算后的 `assignment_version` |
| `Serialization` | **序列化格式（按主题族）**：`md.*` / `signal.*` / `factor.*` / `alarm.*` 可切换；`ctl.*` / `ops.*` 固定 JSON | 全部收发事件的节点（02/04/05/06/07 及各节点内嵌的事件中心适配层） | 广播通知 → 拉取应答 `ConfigSnapshot`；同族生产方与全部消费方必须同版本收敛（03 §6） | 域版本 u64 + 逐族格式取值 |
| `InstrumentBlocklist` | **交易对黑名单**：标的级排除集（下架/暂停/风险标的） | 02 采集（执行）；控制面指派器（标的集计算）；05/07 可选过滤 | 广播通知 → 拉取应答 `ConfigSnapshot`；变更后触发指派重算，采集侧最终表现为 `SubscribePlan` 下发 | 域版本 u64；采集侧生效体现在 `assignment_version` |

### 2.1 域间关系

- **黑名单 ⊂ 白名单计算**：`SubscribePlan` 域给出候选标的集，`InstrumentBlocklist` 从其中剔除，
  剔除结果才是 `ShardPlan.instruments`。黑名单独立成域（而非写死在订阅计划文档里），
  是为了在标的下架/恢复时独立审计与独立回滚。
- **承载上限 ⊂ 指派**：`ProcessCapacity` 与 `SubscribePlan` 共同决定每实例的 `SubscribePlan`，
  前者给约束与策略，后者给标的与通道。
- **序列化 ⊥ 其余七域**：它约束的是事件中心线上格式，与配置内容无关；`ctl.*` / `ops.*`
  固定 JSON 是其默认取值且不开放切换——引导面不能依赖「自身尚未拉到的配置」。

### 2.2 传播方式分类

| 类别 | 域 | 通知 | 交付本体 |
|---|---|---|---|
| **A：广播通知 + 定向应答** | `SignalRules` / `AlertRules` / `FactorRules` / `Channels` / `Serialization` / `InstrumentBlocklist` | `ctl.<domain>` 上 `ConfigChanged`（只带域与版本） | `ctl.request.<instance>` 拉 → 控制面在 `ctl.<node_kind>.<instance>` 回 `ConfigSnapshot` |
| **B：A + 定向推送** | `SubscribePlan` | 同上 | 另有加速路径：控制面直接推 `ctl.collector.<instance>`（snapshot/diff，10 §4.1）。**拉是正确性保证，推只是加速** |
| **C：不发通知** | `ProcessCapacity` | 无（无外部订阅方） | 本地存储，仅供指派器读取 |

通知允许丢失：每个实例以自身 `instance_id` 独占消费组（与数据信道「多实例共享消费组分摊消费」
相反，通知必须人人收到）；即便丢失，心跳收敛比对会触发重推（§4.4），因此通知是加速而非保证。

### 2.3 采集节点登记与配置生成

操作者在控制面**新建采集节点**：**名称即唯一标识**（= `instance_id`），并声明该节点的期望范围
（交易所 / 市场类型 / 数据类型 / 交易对集）与运行参数。

| 项 | 内容 |
|---|---|
| **节点定义** | 控制面**内部状态**（与 catalog 同类，**不新增配置域**）：记录名称、期望范围、运行参数、`host` 映射（由 register 上报回填）、历史 `assignment_version` |
| **生成配置** | 控制面**导出**该节点的配置文件（`instance_id` + 控制面地址 + 运行参数，可带一份冷启动兜底计划）。**只生成内容，不远程部署**——拉起进程归部署方（01 M3） |
| **host 维度** | 采集进程 register 时上报 `host`（03 §5.3 `OpsHeartbeat.host`）；控制面按 `host` **分散分片**，避免同一交易所的分片全落一台机器 |
| **分片** | 操作者只声明范围；**切分片由控制面做**（§5.1~§5.3），超出单实例承载上限时自动切给多个实例 |
| **同名重登** | 同名 = 同一实例重登：**保留历史 `assignment_version` 并继续递增**（否则被采集侧强序门拒收）、清除失联状态、重新纳入候选集；`host` 变化则记录并告警，**不自动杀进程** |

> 与「订阅计划」域的关系：节点定义是**操作者输入**，订阅计划是**它的派生产物**（经指派计算）。
> 运行中的节点只消费 `SubscribePlan`，不消费节点定义本身。
>
> **持久化**：节点定义、catalog、配置版本、运行时状态均落在**控制面数据库**（SQLite），
> 表结构与迁移见 **12-控制面数据库**。

### 2.4 定时任务：交易对信息同步（币信息的外部同步另见 `docs/14 §3`）

控制面内置**定时任务模块**，**每 5 分钟**从各所拉取一次**交易对信息**，作为指派与
发现的上游事实来源。

**同步目标 = `exchange` + `exchange_market` 中 `enabled=1` 的 (venue, market)**——
**不是** `SubscribePlan` 域：后者是"采集意图"（派生自节点 scope，冷启动为空，会造成
"先有鸡还是先有蛋"的死锁），而 `exchange_market` 是"接入台账"。目录同步要回答的是
"这个所有什么标的"，不是"我要采什么"。**catalog 不受黑白名单影响**（`docs/14 §1`）。

| 项 | 内容 |
|---|---|
| **频率** | 每 5 分钟一轮，对 `SubscribePlan` 覆盖到的每个 (venue, market) 各拉一次 |
| **交易对信息** | 经 dig3 连接器层 `get_exchange_info(AccountType) -> Vec<SymbolInfo>`：状态、价格/数量精度、`tick_size`/`step_size`、最小名义额、`instrument_type`、`extra`（所方原始记录透传）。**分工**：transport（端点发现、限速、超时、镜像路由）归 dig3，**平台语义归控制面** —— dig3 刻意保留所方原值（`status` 是 `TRADING`/`BREAK` 裸值；现货记录没有 `pricePrecision`，它兜底成 8；永续 `symbol` 是 `BTCUSDT_PERP`），控制面 `fetcher::normalize` 把这些归一到 `12 §3.1` 的三态与本平台精度口径。**这 7 个字段直接进 `row_hash`，漏一个 = 全量行 hash 变 = 一次全量指派重算**（回归闸见 `fetcher.rs` 的 `equivalence_with_pre_migration_rows`） |
| **币信息** | **两段**：① 各所口径（precision 等）经 dig3 **`get_currencies()`**（本版本在 dig3 侧新增，带默认 `NotImplemented`，与 `get_exchange_info` 对称）——**没有公开端点的所如实 `WireAbsent`**：Binance 的 coin config 走需签名的 `/sapi/v1/capital/config/getall`，故该所层留空、不猜端点 ② **链/合约地址/Twitter/发行流通 由 CoinGecko 提供**，走**独立 1 小时节拍**的外部同步任务（`docs/14 §3/§5`，不属交易所取数） |
| **鉴权** | 全部公共端点，无密钥 |
| **配额** | 使用 02 §6 的「元数据」份额（默认 15%），**与采集、回填份额互不串** |
| **变更检测** | 与上一轮 catalog 逐字段比对，**无差异则不产生任何动作**——不 bump 域版本、不发 `ConfigChanged`、**也不发 `md.meta`**（`md.meta` 身份时间随每次轮询变化，若每轮都发则无法跨轮去重 ⇒ 变更检测必须在**生产侧**执行） |

**产物分三路**：

1. **catalog（控制面内部状态）**——不是配置域：它是"从所方拉取的事实"，而非用户配置，
   与 `ProcessCapacity` 同样不广播、无外部消费者。域里可变的部分仍是用户配置
   （白名单、`InstrumentBlocklist`）。
2. **指派输入**——上新/下架/状态或精度变化 → 触发指派重算（§5.4 新增触发行），
   最终以 `SubscribePlan.assignment_version` 落到采集；**上新因此是被发现并主动推送的**，
   采集仍不做发现（02 §4），发现延迟 = 轮询周期 5 分钟 + 指派下发延迟。
3. **`md.meta` 事件**——交易对与币的参考信息发到总线 → 存储层订阅落库 → 数据服务可查。
   **经总线而非直连存储**（红线 4）；控制面是该事件的生产者（它发布 `ctl.*` 之外的
   `md.meta` 不构成拓扑例外，星型只要求不点对点直连）。

## 3. 结构与配置示例

### 3.1 订阅计划（结构引用 03 §5.3）

`SubscribePlan` / `ShardPlan` / `ConfigChanged` 的权威定义在 03 §5.3，本节只述字段用途。

| 结构 | 字段 | 用途 |
|---|---|---|
| `SubscribePlan` | `assignment_version` | 实例级命令强序：旧版丢弃、新版整包应用（10 §4.3）；心跳 `applied_version` 的比对基准。每次向该实例下发（含重推）+1 |
| | `mode` | `Snapshot` = 整包（register 初次下发、指派重算后、拉取应答）；`Diff` = 增量（标的/通道/黑名单局部变更）。两种模式均可整包兜底 |
| | `shards` | 指派给本进程的分片，**可含多所**（02 §4） |
| | `quota_share` | 该进程在 `(venue, 出口IP)` 份额中的分摊值（02 §6 / 10 §4.2）；多所同进程时按所各给一份，所间令牌桶不串 |
| `ShardPlan` | `venue` / `market` / `shard_idx` | 分片标识 `(venue, market, shard_idx)`，逻辑分片 = 所有权/限频/配额单位（02 §4） |
| | `instruments` | 标的集 + instrument meta（精度等）+ 通道集；采集不做发现，只按此执行（02 §1/§3） |
| `ConfigChanged` | `domain` / `version` | 变更定位：哪个域、第几版。**不携带配置本体**——体量大，且按需拉取更稳 |
| | `publisher` / `ts` | 审计：发布者标识（`控制面实例/操作者`，如 `cp-1/alice`、自动化为 `cp-1/api`）与发布时刻 |
| `ConfigSnapshot`（新，见 §4.6） | `domain` / `version` / `payload` | 拉取应答：域文档本体 + 版本；`ctl.*` 固定 JSON，`payload` 即该域 YAML 文档 |

**两层结构**：控制面存**输入**（§3.6 的域文档），派生**输出**（每实例 `SubscribePlan`）。
`SubscribePlan` 是派生物而非域文档——由 `SubscribePlan` 域 + `InstrumentBlocklist` 域 +
`ProcessCapacity` 域 + 活实例清单确定性推导，同时按 `assignment_version` 留内容快照供审计与重推。

### 3.2 信号规则（域 `SignalRules`，参考 05 §2/§3）

一条规则 = 一个 DAG：节点 = 算子（内置，05 §3），边 = 节点 id 引用；`emit` 映射到
`SignalEvent` 字段（03 §5.3）。**条件表达式 `all` / `any` / 叶子 `{field, op, value}` 与告警规则共用同一套 schema**（§3.3）。

```yaml
# 域 SignalRules —— 信号规则（RuleGraph DAG，05 §2）
version: 7                                  # 域版本，由控制面在发布时赋值
rules:
  - signal_id: btc_4h_momentum              # → SignalEvent.signal_id，稳定 ID，告警按它匹配
    signal_name: BTC 4h 动量                # → SignalEvent.signal_name
    timeframe: 4h                           # → SignalEvent.timeframe
    scope:                                  # 作用标的（canonical，02 §3），黑名单仍全局生效
      - binance:swap:*
      - okx:swap:BTC-USDT
    inputs:                                 # 输入主题：行情 + 因子并列（05 G5 / 07）
      - md.candle.1m
      - factor.funding_basis
    graph:                                  # 节点 = 算子；in = 上游节点 id 列表（DAG 边）
      - { id: close, op: pick,  args: { input: md.candle.1m,        field: close } }
      - { id: basis, op: pick,  args: { input: factor.funding_basis, field: value } }
      - { id: rsi,   op: rsi,   args: { period: 14 }, in: [close] }
      - { id: ma,    op: ema,   args: { period: 50 }, in: [close] }
    emit:
      value: rsi                            # → SignalEvent.value，阈值判定主判据（06 §2）
      payload: [rsi, ma, basis]             # → SignalEvent.payload，告警可引用字段集（05 §4 / 06 §2）
      direction:                            # → SignalEvent.direction，Long/Short/Flat
        long:  { all: [ { field: rsi, op: ">", value: 70 },
                        { field: basis, op: "<", value: -0.01 } ] }
        short: { all: [ { field: rsi, op: "<", value: 30 } ] }
        default: Flat
```

### 3.3 告警规则（域 `AlertRules`，收敛 06 §2 候选）

条件结构与 §3.2 的 `when` / `direction` 完全一致；`route` 引用**渠道 id**，webhook 与凭据收敛在
渠道域（§3.4），避免同一 secret 散落在多条规则里。

```yaml
# 域 AlertRules —— 告警规则（独立于信号规则，06 §2）
version: 21
alerts:
  - rule_id: btc_4h_rsi_overbought          # → AlarmEvent.rule_id，稳定 ID
    name: BTC 4h RSI 超买
    match:                                  # 只对该信号（可按族 / 标的 / 方向 / 配置版本过滤）
      signal_id: btc_4h_momentum
      # instrument: [binance:swap:*]
      # direction: [Long]
    when:                                   # 引用信号事件 payload 字段（05 §4）
      all:
        - { field: rsi,   op: ">", value: 70 }
        - { field: basis, op: "<", value: -0.01 }
      # any: [ ... ]                        # OR，可与 all 嵌套
    window:
      occurrences: 2                        # 时间窗内 N 次才判触发
      within: 10m
    level: Warn                             # → AlarmEvent.level：Info / Warn / Critical
    route:
      - { channel: feishu, target: ops-room }   # channel 引用 §3.4 的 id
    throttle: 5m                            # 节流/去重（06 §4 alarm_id 幂等）
```

条件 schema（两处共用）：

| 形态 | 含义 |
|---|---|
| `{ field, op, value }` | 叶子：对 `field` 施加 `op`（`>` / `>=` / `<` / `<=` / `==` / `!=`）与 `value` 比较 |
| `all: [...]` | AND（默认组合方式） |
| `any: [...]` | OR |
| `window: { occurrences, within }` | 时间窗内命中 N 次才成立 |
| `match` / `when` / `route` / `throttle` | 仅告警规则具备：匹配面、条件、去向、节流 |

### 3.4 渠道配置（域 `Channels`）

```yaml
# 域 Channels —— 渠道后端（06 §3，一期飞书/钉钉）
version: 5
channels:
  - id: feishu                             # 被 AlertRules.route.channel 引用
    backend: feishu                        # 适配器名：feishu / dingtalk（二期 phone_sms / mail / webhook）
    endpoint: "https://open.feishu.cn/open-apis/bot/v2/hook/****"
    retry:   { attempts: 3, backoff: 2s }
```

## 4. 版本与发布流程

### 4.1 版本模型

四类版本各司其职，不可合并（对比 03 §5.4 的 `event_id` / `x_version`）：

| 版本 | 载体 | 单位 | 用途 |
|---|---|---|---|
| **域版本** `domain.version` | 配置存储、`ConfigChanged`、`ConfigSnapshot` | 配置域 | 发布批次、审计、回滚锚点、心跳收敛判据 |
| **`assignment_version`** | `SubscribePlan` | 实例 × 命令 | 命令强序：旧版丢弃、新版整包应用；采集 `applied_version` 的比对基准 |
| **事件内 `version`** | `SignalEvent` / `FactorEvent` | 事件 | 溯源「哪次配置产出」，取值 `v<域版本>` |
| **`event_id` / `x_version`** | 信封 | 事件 | 幂等与定序（03 §5.4），与配置版本无关 |

**域是唯一版本单位**：规则级不单独版本化。同一域内某条规则未变也随域发布获得新版本号，
事件 `version` 因此表示「产出该事件时的配置世代」；规则级差异由版本历史的文档 diff 给出。

域版本与 `assignment_version` 的关系：前者标识**计划输入文档**，后者标识**下发给某实例的命令序号**。
一次域发布可能对同一实例下发多次（初发、Diff、重推），`assignment_version` 每次 +1，
故「最大版本 = 最新一次下发」，收敛判据不会歧义。

### 4.2 存储与审计

> 持久层实现（表结构、DDL、迁移）见 **12-控制面数据库**；本节只述语义。

| 要素 | 约定 |
|---|---|
| 存储形态 | 每域一条**追加式版本历史** + `current` 指针；历史内容不可变。后端可为嵌入式数据库或版本化文件树，抽象边界 = 「按域取版本内容 / 写新版本 / 读历史」 |
| 审计条目 | 每次发布写不可变记录：域、版本、`publisher`、时间、变更摘要（与上一版的文档 diff）、原因/工单号 |
| 元数据 | instrument meta（精度等）随 `SubscribePlan` 域一同存放（M1），变更走同一发布流程 |
| 派生物快照 | 每次下发的 `SubscribePlan` 按 `assignment_version` 存内容快照，供重推与审计 |

### 4.3 发布流程

```
操作者 / 自动化
   │ ① 提交域文档 → 控制面校验（schema + 跨域引用：告警引用的 signal_id 存在、route.channel 存在）
   ▼
控制面：域 D 版本 v → v+1（内容入历史，current 指针前移，写审计条目）
   │ ② publish ConfigChanged{D, v+1, publisher, ts} → ctl.<D>
   ▼
事件中心 ──► 该域各消费实例（group = instance_id，各收一份）
   │ ③ 实例发 ctl.request.<instance>（携带 applied_version）
   ▼
控制面 ── ④ 应答 ConfigSnapshot{D, v+1, payload} → ctl.<node_kind>.<instance>
   │      （SubscribePlan 域应答 SubscribePlan；采集另有定向推送，10 §4.1）
   ▼
实例本地校验 → 应用（重建 DAG/规则集/渠道表/序列化器）
   │ ⑤ 下一心跳 OpsHeartbeat.applied_version + counters["cfg.<D>"] = v+1
   ▼
控制面消费 ops.* → 比对收敛（§4.4）→ 更新快照键
```

- 校验在写入侧完成；实例侧仍做一次轻量校验（schema/引用），校验不过则**不应用、维持当前版本**。
- 应用失败不产生专门的反馈消息：其唯一出口是心跳版本不收敛（§4.4）。

### 4.4 收敛判据

| 实例类型 | `applied_version` | 逐域判据 |
|---|---|---|
| 02 采集 | = `assignment_version`（10 §4.3） | `applied_version == 最新 assignment_version` |
| 05 / 06 / 07 | 最近一次应用动作的域版本 | `counters["cfg.<domain>"] == 该域当前版本`（对每个消费域） |
| 02/04/05/06/07 的事件中心适配层 | 同上 | `counters["cfg.serialization"]` |
| 控制面 | `None`（它是版本来源） | `counters["cfg.<domain>"]` = 各域**当前**版本，供 06 比对 |

- **心跳承载多域版本**：`OpsHeartbeat.applied_version` 是单值，逐域版本放 `counters`（`BTreeMap<String,i64>`，03 §5.3），
  键约定 `cfg.<domain>`（如 `cfg.signal_rules`）。采集因只有一个强序域，两者取值相同。
- **收敛目标**：应用后下一心跳（≤ 5s）反映；**不收敛超时默认 30s**（6 个心跳周期）→ 控制面重推 ①；
  仍不收敛 → 计入 `ops.control` 的不收敛计数器，由 06 按告警规则判定（控制面不产 `alarm.*`，§6.5）。
- 不收敛超时、心跳间隔等为控制面自身运行参数，存于控制面内部，不构成对外配置域。

### 4.5 审计与回滚

- **审计** = §4.2 的不可变历史条目；「改了什么（diff）、谁改的（`publisher`）、何时改（`ts`）、为何改（原因）」均可查。
- **回滚 = 版本历史恢复**：取历史版本内容**重新发布为新版本**（版本号继续单调），
  而不是把 `current` 指针倒回旧号——版本倒流会使收敛判据（`== 当前版本`）出现「已收敛的实例反而
  显示落后」的歧义。回滚本身也走 §4.3 全流程，产生新审计条目（`reason: rollback to vN`）。
- **与运行时应用失败回滚是两件事**：后者（实例报错 → 控制面自动撤回配置）已排除（§7），
  控制面不接收应用失败反馈、不自动撤回；实例侧失败表现为版本不收敛，由 06 观测处置。

### 4.6 协议层需要补的应答结构

`ConfigChanged` 明确不带配置本体（03 §5.3），`CtlMessage` 现只有 `SubscribePlan | ConfigChanged`
两个变体，**没有承载「配置体」的通用变体**。为使「引擎经 `ctl.request` 拉取」闭环，需在 03 §5.3 登记：

| 结构 | 字段 | 说明 |
|---|---|---|
| `CtlMessage::ConfigSnapshot` | `domain: ConfigDomain` | 应答的域 |
| | `version: u64` | 该域版本 |
| | `payload: <JSON 文档>` | 域文档本体；`ctl.*` 固定 JSON，故直接为 JSON |

不采用「配置体改走控制面 HTTP 接口」的方案：全平台单一传输已定（10 §2），且 `SubscribePlan`
的拉取应答已定义在命令信道上，两套应答路径会使收敛与审计分叉。

## 5. 分片 → 进程指派

### 5.1 切分片 `(venue, market, shard_idx)`

| 项 | 约定 |
|---|---|
| 分片单位 | `(venue, market, shard_idx)`：逻辑分片是所有权、限频、配额单位；进程是承载容器，可跨所（02 §4） |
| 切分算法 | 每个 `(venue, market)` 内，标的按 `hash(instrument)` 均匀映射到 `shard_idx`；`shard_count = 2^ceil(log2(ceil(n / shard_size)))`，`shard_size` 取自 `SubscribePlan` 域 |
| 稳定性 | 分片数取 2 的幂：标的增删只改写自身归属；跨越幂边界翻倍时，约半数标的留在原分片，避免全量重切 |
| 分片内容 | `ShardPlan.instruments` = 白名单候选 − 黑名单 + instrument meta + 通道集（§2.1） |

### 5.2 承载约束

| 约束来源 | 内容 |
|---|---|
| `ProcessCapacity` 域 | `max_shards_per_process` / `max_instruments_per_process` / `max_channels_per_process`（配置项，默认值按 dig3 连接器层内存实测定，02 §7） |
| register 自报能力 | 实例在 register 中上报「可装哪些所、多少分片」（10 §5） |
| 指派取值 | 每实例可用容量 = **min(域配置上限, register 自报能力)**；不满足任一条则该实例不再纳入候选 |

`ProcessCapacity` 的消费者是指派器，不产生总线通知；它的变更经指派重算，最终以
`assignment_version` 变化被采集感知。实例侧不需知道本域内容——它只按收到的 `SubscribePlan`
执行，超限的计划在 §5.4 的重算阶段就不会生成。

### 5.3 分布策略与取舍

| 策略 | 失效域 | 配额 | 连接/内存 | 运维归属 |
|---|---|---|---|---|
| **`scatter`（同所打散，默认）** | 单进程挂 → **每个所各损失一部分**，无任一所全断 | 同所份额被 N 个进程分摊，每进程令牌桶额度 = 份额 / 持有该所的进程数 | 每进程跨所，连接数按「所 × 通道」累加，内存占用更均匀 | 进程与所的对应关系不直观 |
| **`aggregate`（同所聚合）** | 单进程挂 → **该所全部数据断**（02 §6 已列的已知代价） | 该所份额集中在一个进程，桶额度高 | 进程按所隔离，便于单独限频与排障 | 归属清晰，单所排障不动其它 |

默认取 `scatter`：失效域是平台首要代价（02 §6），且打散后单点故障不构成「任一所的单点」。
策略是配置项，按可用性诉求切换，不改代码。

**host 维度（与上面两个策略正交）**：候选实例先按 `host` **交错排序**再做 round-robin 放置
（§2.3），使连续几次挑选落在不同机器上——同一交易所的分片不会连续堆在一台机上；
`host` 未上报（`None`）的实例排在最后。实例迁移后心跳刷新 `host`，下次重算即生效。

`quota_share` 的分摊随 `scatter` 变化：控制面在生成 `SubscribePlan` 时，按该进程实际持有的
所与进程数算好分摊值下发，进程内按所各建令牌桶（02 §4），所间不串。

### 5.4 指派流程与触发条件

| 触发 | 动作 | 下发 |
|---|---|---|
| 实例 register | 记录能力 → 指派（初次） | `Snapshot`（10 §5：register 后即回初始计划，省一次拉取） |
| `SubscribePlan` 域发布 | 重算受影响实例 | 变更局部 → `Diff`；分片重切 → `Snapshot` |
| `InstrumentBlocklist` 域发布 | 重算（黑名单参与标的集计算） | 同上 |
| `ProcessCapacity` 域发布 | 重算（约束/策略变化） | 同上 |
| 实例 shutdown / 失联 | 标记状态、关闭会话 | **不自动再指派**（§7 排除）；恢复由实例重启 register 触发 |
| 定时任务发现标的变更（上新/下架/状态或精度变化，§2.3） | 更新 catalog → 重算受影响实例 | 同 `SubscribePlan` 域发布：局部 `Diff` / 分片重切 `Snapshot` |
| 定时任务发现**无**变更 | 不动作 | 无（不 bump 任何版本） |
| 控制面重启 | 从快照键 + 版本历史恢复后按需重推 | `Snapshot`（`assignment_version` 递增） |

算法：候选实例按策略排序 → 逐分片分配，检查三条容量约束 → 生成每实例 `SubscribePlan`
（含 `quota_share` 分摊）→ 按 `assignment_version` 下发并存快照。

## 6. 控制信道消费

> 语义、频率、时序见 10 §5；本节只述控制面的接收与处理，不重复细节。

### 6.1 接收面

- 控制面以消费组读取 `ops.<node_kind>.<instance>`，与 06 订阅**同一主题**（10 §5）；
  **不代发、不 fan-out**，06 的观测面与控制面的观测面同源。
- 按实例命名的主题（`ops.<kind>.<instance>`、`ctl.request.<instance>`、`ctl.<kind>.<instance>`）
  由控制面在 register 时建立会话、shutdown/失联后关闭；通配订阅仅在 backend 能力表
  （03 §4.5）声明支持时作为优化，不作依赖。

### 6.2 三类消息的处理

| 消息 | 控制面动作 |
|---|---|
| **register** | 记录 `instance_id` / `node_kind` / 自报承载能力 / 启动时间 → 写快照键 → 指派（§5.4）→ 经命令信道回初始 `SubscribePlan` snapshot |
| **heartbeat**（5s） | 更新快照键（状态、`applied_version`、`counters`、`last_seen_ts`）→ 逐域收敛比对（§4.4）→ 不收敛则重推 |
| **shutdown** | 标记正常下线、关闭该实例的主题会话、快照键 `status = Stopped` |

### 6.3 兜底快照键

| 项 | 约定 |
|---|---|
| 内容 | 每实例一条：`instance_id`、`node_kind`、状态、自报能力、当前 `assignment_version` 与 `applied_version`、`counters`（含 `cfg.*`）、`last_seen_ts` |
| 写入时机 | register / 每次心跳 / shutdown / 判死 |
| 恢复场景 | 控制面重启、消费组重建——从快照键恢复「每实例最新状态」，避免历史心跳过期造成的状态空洞（10 §5） |
| 存放位置 | **控制面自身的状态存储**（与配置存储同库）。事件中心明确不提供 K/V 查找（03 §3），快照键不占总线能力 |
| 与 06 的关系 | 06 直接订阅 `ops.*` 自建观测面，不读本键；本键只服务控制面自身的指派与收敛判断 |

### 6.4 失联判定

判定规则（`shutdown` 缺失 + 心跳断 3×5s → 判死）与总线故障的已知代价均见 10 §5，此处不重复。
控制面侧动作限定为：快照键 `status = Dead`、关闭该实例主题会话、将失联计数写入 `ops.control` 计数器；
**不触发任何自动指派变更**（§7），失联告警由 06 从同一订阅面判定产出。

### 6.5 控制面自身的心跳

- 控制面发布 `ops.control` 心跳（`NodeKind::Control`，03 §5.3），`status` 随生命周期变化，
  `counters` 携带各域**当前版本** `cfg.<domain>` 与不收敛/失联实例计数。
- 控制面**不消费自己的主题**，也不产生 `alarm.*`：不收敛、失联等事实以 `ops.control` 的
  计数器与状态表达，由 06 按告警规则判定并产告警（O2，星型拓扑下不代发）。
- 06 的平台告警规则因此可直接以 `cfg.<domain>` 与不收敛计数器为阈值条件，无需控制面另有出口。

## 7. 明确排除

| 排除项 | 说明 |
|---|---|
| **再平衡防抖**（及一切失联驱动的自动再指派） | 失联只标记状态与告警，不改任何分片归属；变更指派的唯一途径是域发布或实例 register（10 §5/§8） |
| **配置应用失败反馈与运行时回滚** | 无失败反馈消息、无自动撤回；失败唯一出口 = 心跳版本不收敛 + 06 告警。审计意义上的回滚是 §4.5 的版本历史恢复，二者不混 |
| **控制面 HA** | 单实例运行；重启后从自身配置存储与状态存储恢复。不设计多实例主备、选主、脑裂处理 |
| **部署编排** | M3：无 Kubernetes / 容器 / systemd 运维方案；进程起停与拓扑属平台使用者 |

其余排除项（背压、pause/resume/kill 指令、gap 登记、backend replay 作为命令送达保证）见 10 §8；
配置面的协议协商不设（03 §6）。

## 9. 实现事项

1. **协议登记**：`ConfigDomain` 枚举取值（§2 表首列）、`CtlMessage::ConfigSnapshot` 结构、
   `ctl.<domain>` / `ctl.<node_kind>.<instance>` 主题通则——对齐 03 §5.2/§5.3/§8。
2. **配置存储**：每域追加式版本历史 + `current` 指针 + 不可变内容；按域取版本内容 / 写新版本 / 读历史的抽象接口。
3. **审计条目**：域、版本、`publisher`、时间、文档 diff、原因；回滚作为一次正常发布写入（§4.5）。
4. **写入校验**：八个域的 schema 校验与跨域引用检查（告警 `signal_id`、`route.channel` 存在性、
   黑名单标的格式、DAG 无环与算子存在性）。
5. **发布器**：`ConfigChanged` → `ctl.<domain>`；`ConfigSnapshot` / `SubscribePlan` 应答 → `ctl.<kind>.<instance>`；
   `ProcessCapacity` 域跳过通知（§2.2 C）。
6. **指派器**：稳定哈希分片（§5.1）→ 容量约束求解（§5.2）→ 分布策略（§5.3）→
   每实例 `SubscribePlan`（`Snapshot`/`Diff`、`assignment_version`、`quota_share` 分摊）与内容快照。
7. **控制信道消费**：按实例会话的建立与关闭、`register`/`heartbeat`/`shutdown` 处理（§6.2）、
   快照键读写与恢复（§6.3）、失联标记（§6.4，判定规则引用 10 §5）。
8. **收敛监控**：心跳 `applied_version` + `counters["cfg.<domain>"]` 比对、超时重推、
   不收敛与失联计数写入 `ops.control`。
9. **控制面自身心跳**：`ops.control` 发布（`NodeKind::Control`、生命周期状态、各域当前版本与计数器）。
10. **配置 schema 落地**：§3 的 YAML 与解析类型，作为 05/06/07 各篇候选 schema 的收敛结果；
    条件表达式（`all`/`any`/叶子/window）实现一份，信号 `emit.direction` 与告警 `when` 共用。
11. **测试**：发布 → 通知丢失 → 拉取应答的闭环；旧 `assignment_version` 丢弃与整包应用；
    回滚发布后收敛判据仍单调；多域并发发布时 `counters` 逐域正确。
