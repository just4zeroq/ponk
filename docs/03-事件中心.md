# 03 事件中心（EventCenter）

本文档定义 PONK 平台的事件中心：一层**消息抽象**（trait + 消息协议 + backend 适配 + 能力表）。
它是全平台的交换枢纽，但**本身不是可部署的组件**。

---

## 1. 定位

事件中心由三部分构成，只有第二部分需要部署：

| 部分 | 内容 | 是否常驻进程 |
|---|---|---|
| **事件中心抽象层**（本平台代码） | `EventCenter` trait、统一消息协议、backend 适配器、能力表 | 否——以库的形式编入每个节点进程 |
| **消息中间件 runtime** | Redis / Kafka / NATS / Iggy 服务端 | 是，但属外部组件，只部署不开发 |
| **总线配套后台** | 死信消费、保留清理、主题初始化 | 否，见 §7.4 |

推论：

- 架构图中的"事件中心"指**逻辑枢纽**，不是一台机器；节点是链接该库的进程。
- 扩容只涉及消息中间件 runtime，不存在"事件中心服务扩容"。
- **拓扑为星型**：节点之间不直接通信，一切事件交互经事件中心；唯一例外是查询面直读存储后端。

## 2. 设计原则：契约层与能力层分离

若把"分区""重放"等特性直接写进抽象 API，薄后端（Redis Streams 无分区、重放能力受限）会被排除；
若完全不设约束，后端差异又会泄漏到上层。因此抽象分两层：

- **契约层（§3）**：所有 backend 必须满足的最低公共语义，抽象 API 以此为界。
- **能力层（§4）**：后端具备的额外特性，通过能力表查询，上层按能力分支。

## 3. 契约层

| 语义 | 约定 |
|---|---|
| **投递** | 写入侧 at-least-once（消息可重复，消费方须幂等）；**消费侧无 ack**，读取即推进消费位点（§4.4） |
| **顺序** | 尽力有序：同一（主题, 分区键）内尽量有序，跨键无顺序承诺；**不承诺全局有序** |
| **消费** | 消费组：多个消费者共享同一主题的消费，各自推进、互不干扰 |

**明确不提供**（写入契约会排斥薄后端）：全局有序、事务性保证、后台重放、K/V 查找。

## 4. 接口

### 4.1 三个原语

```rust
pub trait EventCenter: Send + Sync {
    /// 发布。数据信道、命令信道、控制信道共用，不做区分（见 10）。
    fn publish(&self, topic: &Topic, envelope: &Envelope) -> Result<(), ECError>;

    /// 打开「消费组 × 主题」的读取会话。
    fn open(&self, topic: &Topic, group: &Group, opts: SessionOpts)
        -> Result<Box<dyn Session>, ECError>;

    fn capabilities(&self) -> Capabilities;
}

pub trait Session {
    /// 按调用方节奏取消息；`Ok(None)` 表示超时无消息，非结束。
    /// 读取即推进消费位点（**无 ack**，见 §4.4）。
    fn next(&mut self, timeout: Duration) -> Result<Option<Envelope>, ECError>;
    fn close(&mut self) -> Result<(), ECError>;
}

/// 死信是独立读取面：`dlq.*` 的线负载为 DeadLetterMeta（非 Envelope，类型不同），
/// 故不进 Session；供运维工具查看与人工重投（§7.4）。
pub trait DeadLetterReader {
    fn dead_letters(&self, topic: &Topic, limit: usize) -> Result<Vec<DeadLetter>, ECError>;
}
```

### 4.2 订阅与拉取

两种消费方式**都支持**，且共享同一消费组会话：**订阅是拉取的语法糖**（内部为
`loop { session.next() -> handler }`），不是第二条通路。

```rust
pub fn subscribe<C, H>(center: &C, topic: &Topic, group: &Group, handler: H)
    -> SubscriptionHandle
where C: EventCenter, H: FnMut(Envelope);
```

- 拉取式为**核心原语**，服务需要自控节奏的消费方（信号引擎按 DAG 节奏喂数据，回放时尤其如此）。
- 订阅式服务不关心节奏的消费方（告警、心跳监听）。

### 4.3 能力查询

`capabilities()` 返回 §4.5 所列能力表；上层据此分支，不假设后端具备某特性。

### 4.4 确认语义：无 ack

不提供 ack 原语；读取即推进消费位点（backend 默认行为：Redis 随读 XACK，Kafka 自动提交偏移）。

- 投递语义为：消息写入 backend → 被消费方拉取 → 视为已消费。
- **一致性由下游保证，不由总线保证**：
  1. 幂等 `event_id`（§5.4）使重复写入在存储层被去重与 upsert 消化；
  2. 数据缺失的发现与补救由数据检查与修复节点负责（01 §7）。
- **已知风险**：在"拉取后、处理完成前"崩溃的窗口内消息不会补投；该窗口内丢失的不可补
  数据（ticker、trade）无法追回。窗口极小，接受此风险以换取接口简洁。

### 4.5 能力层

| 能力 | 含义 |
|---|---|
| `partitioning` | 是否支持分区、可配分区数 |
| `replay` | 是否保留消息、是否支持按时间或偏移重放 |
| `dead_letter` | 能否按主题建立独立死信流（**不含自动重投**，见 §7.4） |
| `retention` | 持久化与保留策略 |

能力取值来自实测而非手写标记。

### 4.6 会话选项

`SessionOpts`：消费超时、起始位置（latest / earliest / 指定偏移）。

## 5. 消息协议

### 5.1 两级信封：公共头 + 家族体

所有事件共用**一个信封骨架**，但只有**跨家族都有意义**的字段留在头部；行情专属字段
（标的、交易所时间）下移进家族体。

理由：若把 `venue / market / native_code / exchange_ts` 放进公共头，非行情事件
（心跳、配置变更、告警）没有这些语义，只能填占位值，会污染按 venue 的过滤与索引；
而且单值的 `venue` 无法表达含多所分片的 `SubscribePlan`；最后，`SignalEvent` 已自带
`instrument` 与 `timestamp`，公共头再存一份会产生无编译期保护的漂移。

```rust
pub struct Envelope {
    pub event_type: EventType,   // 解析与路由（§5.2 注册表）
    pub shard: Option<String>,   // 分片键：预计算的 instrument_id；None → 默认分区
    pub event_id: String,        // 幂等（§5.4）
    pub received_ts: u64,        // 观测与定序（采集/产生时刻，ms）
    pub x_version: Option<u64>,  // 定序版本，K 线族需要（身份时间 = bar 起点）
    pub source: NodeId,          // 产生该事件的节点实例（观测用）
    pub body: Body,
}

pub enum Body {
    Market(MarketBody),          // 行情 md.*
    Signal(SignalEvent),
    Factor(FactorEvent),
    Alarm(AlarmEvent),
    Ops(OpsHeartbeat),
    Ctl(CtlMessage),             // SubscribePlan | ConfigChanged | ConfigSnapshot
}
```

留在信封的字段都满足「跨家族有意义」：路由（`event_type`、`shard`）、幂等（`event_id`）、
观测（`received_ts`、`source`）、定序（`x_version`）。

- **`enum Body` 使"没有这个字段"在编译期成立**，而不是"填一个 None"；
  反序列化按 `event_type` 分派到对应变体。
- **`shard` 预计算**：backend 适配器只读该字段做分区映射，不必理解 body 结构；
  无标的的事件为 `None`，进入默认分区（总线不需要按标的对它们排序）。

### 5.2 事件类型注册表

| `event_type` 家族 | 主题前缀 | 负载结构 | 语义与生成规则 |
|---|---|---|---|
| 行情 | `md.*` | `MarketBody`（§5.3，含 venue/market/native_code/exchange_ts）+ 复用 dig3 `core::types`（不自定义） | 02、09 §2.3 |
| 信号 | `signal.*` | `SignalEvent`（§5.3） | 05 |
| 因子 | `factor.*` | `FactorEvent`（§5.3） | 07 |
| 告警 | `alarm.*` | `AlarmEvent`（§5.3） | 06 |
| 心跳 / 指标 | `ops.*` | `OpsHeartbeat`（§5.3） | 10 §5 |
| 命令 / 配置 | `ctl.*` | `CtlMessage` = `SubscribePlan \| ConfigChanged \| ConfigSnapshot`（§5.3） | 10 §4、09 |
| 死信 | `dlq.<topic>` | 原负载 + `DeadLetterMeta`（§5.3） | §7.3 |

**本表是 `event_type` 枚举的唯一登记处**；新增家族须先登记，避免出现私有主题。

> `core::types::market_data` 是**模块**不是类型，因此 `MarketBody::data` 是**按通道的分派枚举
> `MarketData`**，各变体原样承载 dig3 类型、本层不重定义字段；唯一平台自建的是 `Meta` 变体里的
> `CurrencyInfo`（dig3 无 `Currency` 类型）。

**职责划分**：结构（类型、字段、序列化）集中在协议层，供全部组件共享；模块文档只描述
字段语义与生成规则，不重复结构定义。因此：

- 修改 §5.3 任一结构 = 修改全平台协议，所有节点重编译——**高变更门槛**；
- 修改模块逻辑而不动结构（例如信号将新的中间量写入已有的 `payload`）不触发该门槛。
  开放字段（`payload`、`meta`、`counters`）即为承载常变明细而设。

### 5.4 幂等键与版本号

两项独立设计，不可合并：

- **`event_id`（幂等，须内容敏感）**
  `身份键 : event_type : 身份时间 : 内容哈希`，其中**身份键按家族取值**：
  行情/信号/因子用 `instrument_id`，告警用 `alarm_id` 的规则与触发源，心跳用 `instance_id`，
  命令用 `assignment_version` 或 `domain+version`——即身份键始终是"这条事件相对于谁唯一"。
  哈希在**规范化视图**（递归键排序）上计算——既不依赖第三方库的默认键序，也**与线上
  序列化格式无关**，因此更换格式不改变 `event_id`，去重与替换语义不漂移。
- **身份时间与 `x_version` 按家族从负载推导**（`event_type` 只到家族，区分不了 `md.candle.1m`
  与 `md.trade`）：K 线族的身份时间 = 负载的 bar 起点（`open_time`），trade/ticker/l1 =
  各自的成交或推送时间；`event_type` 家族 + 负载类型共同决定推导规则。
- **`x_version`（定序，须单调）** 取 `received_ts`，适用于**全部 K 线周期**（不只 1m）——
  同一根 bar 的多次更新身份时间不变，仅靠 `event_id` 会使版本停滞，故另设 `x_version`
  作为替换定序版本（存储侧按其取最新）。
- 其余事件族身份时间每次推送均变，仅用 `event_id` 即可。

### 5.5 数值约定

- **平台自建负载**（`SignalEvent` / `FactorEvent` / `AlarmEvent` / `OpsHeartbeat` / `CtlMessage`）
  中的价量类字段（若有）与 `meta`/`payload` 里的十进制值，用**十进制字符串**表达，避免二次精度损失。
- **行情负载 `MarketBody.data` 沿用 dig3 类型，其价量为 `f64`**（§5.2 的复用约定）——
  为此**接受入站精度损失**，与既有结论「数值等价」一致。若未来要求全链路无损，
  需放弃复用 dig3、自建字符串化行情结构（E5 反向，代价大，属远期议题）。

## 6. 序列化

序列化是协议的内部实现，不属于契约层；更换格式不改变任何上层代码。

| 格式 | 保真 | 体积 / 吞吐 | 用途 |
|---|---|---|---|
| **JSON（默认）** | 价量为字符串，无损 | 中 | 默认；死信与运维工具可直接阅读 |
| MessagePack | 无损 | 优于 JSON | 吞吐优化项 |
| Protobuf / Avro | 无损 | 最优 | **远期且受限**：非自描述格式无法处理 dig3 类型的 `skip_serializing_if` 与 `serde_json::Value`（实测 `postcard` 往返失败），启用前须先解决这两点 |

- 抽象为 `Serializer` / `Deserializer` trait，**默认 JSON**。
- 配置粒度为**主题族**（`md.*`、`signal.*`、`factor.*`、`alarm.*`），由控制面下发（09 §2
  `Serialization` 域）；同一主题的生产方与所有消费方必须一致。两端均为本平台库，以配置
  一致保证，**不做协议协商**。
- **`ctl.*` 与 `ops.*` 固定 JSON，不开放切换**——引导面不能依赖"尚未拉到的配置"，
  否则格式配置构成自指循环。
- `event_id` 与线上格式无关（§5.4），故格式切换不影响去重与替换语义。

## 7. Backend 适配

### 7.1 支持范围

四款 backend 全部支持，选型为配置项：

| Backend | 契约层 | 能力层 | 定位 |
|---|---|---|---|
| **Redis Streams** | 满足 | 无分区；保留窗口内可经 `XGROUP SETID` / `XRANGE` 回读（受 `MAXLEN` 截断限制，**不承诺跨会话重放**）、XAUTOCLAIM 死信 | 起步选择；单流全局有序蕴含分区有序 |
| **Kafka** | 满足 | 分区、重放、死信、持久化 | 放量候选，引入 JVM 运行时 |
| **Iggy** | 满足 | 分区、持久化、保留、消费组、按偏移读 | Rust 原生，与平台同语言栈，能力待实测 |
| **NATS JetStream** | 满足 | 分区、重放、死信、持久化 | 放量候选，较轻 |

单流后端吞吐见顶是切换分区型后端的信号；除能力分支外，上层不应感知 backend 差异。

### 7.2 回放

平台的回放一律读取**存储层**（04 §4），不依赖 backend 的重放能力——四种 backend 因此在
回放语义上等价。backend 的 `replay` 能力仅作可选加速，不作依赖。

### 7.3 失败处理

发布失败的事件写入 `dlq.<topic>`，携带 `DeadLetterMeta`。

### 7.4 无常驻后台

- **死信只堆积，不常驻消费**：需要时用运维 CLI 工具查看与人工重投。`dead_letter` 能力
  因此仅表示"能否建立独立死信流"。
- **保留清理交给 backend 自带策略**（Redis XTRIM / MAXLEN，Kafka retention 配置）。
- **主题初始化**由 backend 配置或首次写入自动创建（Redis 自动建流；Kafka 由部署配置或
  初始化脚本）。

## 8. 主题命名

| 主题族 | 用途 |
|---|---|
| `md.<channel>` | 行情：`md.candle.1m`、`md.trade`、`md.ticker`、`md.l1`、`md.funding`、**`md.meta`**（交易对/币参考信息，09 §2.3） |
| `signal.<rule>` | 信号 |
| `factor.<rule>` | 因子 |
| `alarm.<rule>` | 告警 |
| `ops.<node>` | 心跳与运行指标 |
| `ctl.<domain>` | 配置变更通知（只带域+版本） |
| `ctl.<node_kind>.<instance>` | 定向命令与拉取应答（通则；`ctl.collector.<instance>` 是其特例，另有 `ctl.signal.*`、`ctl.alert.*` 等） |
| `ctl.request.<instance>` | 拉取请求（携带 `applied_version`） |
| `dlq.<topic>` | 死信 |

分片键由 `Envelope::shard` 承载：**行情/信号/因子**事件为 `instrument_id`（venue, market,
native_code）的稳定哈希；**心跳、告警、配置**等无标的事件为 `None`，进默认分区。
backend 适配器只读 `shard` 做分区映射。同一分片内尽力有序。
