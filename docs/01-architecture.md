## 1. 设计由来

`old/`（TheNextQuant）的核心思想：
- **统一行情对象**：Orderbook / Kline / Trade 三件套，platform / symbol / timestamp 首行字段，
  价量**尽量用字符串保精度**。
- **事件驱动**：Market / Trade / Asset 各服务 → 统一事件中心 → 策略异步回调。
- **全异步单进程模型**：asyncio 事件循环 + RabbitMQ，无多线程/无锁。
- **简化哲学**：一个 Trade 模块管一个平台一个交易对。
- **策略=Python 代码**，靠回调被行情事件驱动，策略频繁更变。

PONK 在本设计中的**处置策略**：
- **语义继承**：统一行情对象、事件驱动、平台与服务解耦。
- **形态重置**：
  - Market 行情服务器 → 直接用成熟多所连接器工具包 **digdigdig3**（47 所 / 18 TRUSTED /
    27 种 DataPoint / 能力表），不重复造连接器。**只依赖 dig3 连接器层与 core 类型，
    不依赖 dig3-station**（station 已从依赖中移除）。
  - RabbitMQ 事件中心 → 抽象成**可插拔 backend 的 EventCenter**（契约层 + 能力层）。
  - Python 策略代码 → 哨兵式**声明式 RuleGraph 信号引擎**（独立进程 + 一等回放/回测）。

## 2. 范围

### 2.1 本期范围（in）

- **行情数据采集**（public market data only）
- **信号计算**（声明式规则 + 内置算子库）
- **监控告警**（主职：信号规则告警；副职：平台性能监控）
- **因子挖掘**（二级事件生产者：原始行情 → 中间量事件）
- **行情数据服务**（一等 SQL/文件导出；二等鉴权 REST/WS 推迟；WS 砍掉）

### 2.2 明确排除（out）

- **交易执行**：下单 / 撤单 / 订单
- **账户 / 持仓 / 资产**（含私有行情管线）
- 私有数据、密钥管理、下单幂等、成交回报对齐、持仓盈亏、爆仓价
- 部署编排（Kubernetes / 容器 / systemd 运维设计，均不纳入本设计）

> 信号只负责「算出来并派发」，接不接执行是下游自己的事；采集仅 public 行情。

## 3. 总体架构图

**拓扑原则：星型，事件中心是唯一交换枢纽。** 存储、告警（监控）、信号、因子、数据服务、
控制面**全部是独立节点**，彼此**不直连**——一切事件交互只经 ① 事件中心；唯一例外是
**查询面**（数据服务/回放直接读存储后端，那是读数据而非事件交换，04 §5）。

```
dig3(采集, public行情)                        ┃ 控制面服务 (配置事实来源)
   │ 27 DataPoint / 能力表 (连接器层)           ┃ · 信号/告警/因子规则·订阅计划·渠道·元数据
   ▼                                            ┃ · 仅广播"配置已变更"通知
① 事件中心 EventCenter (抽象, backend可插拔) ──────┃ · 引擎从控制面拉取配置,部署形式不设计
   │  契约: at-least-once / 尽力有序 / 消费组     ┃
   │  能力表: 分区 / 重放 / 死信 / 持久化         ┃
   ├──────────────┬──────────────┬──────────────┬─────────────┐
② 存储层(抽象)     ③ 信号引擎        ④ 监控告警       ⑤ 因子挖掘        ⑥ 数据服务
CK/duckdb..      ·声明式RuleGraph ·信号告警(主)    ·二级事件源:      ·一等SQL/文件(CK直连)
·订阅事件中心      ·内置算子DAG     ·平台性能监控(副) 原始行情→中间量    ·二等REST待定 ·WS砍掉
·回放/查询源       ·一等回放/回测    ·规则独立配置     ·产物=因子事件
·后端可插拔       ·产出信号事件     ·渠道可插拔      (信号引擎把它当普通输入源)
                                   (飞书/钉钉一期)
```

## 4. 已确认决策清单 (decisive)

### 4.1 采集 (dig3)

| # | 决策 |
|---|---|
| C1 | 采集 = **digdigdig3 连接器层 + core 类型**（27种DataPoint/能力表），不重复造连接器；**不依赖 dig3-station**（已删除）。 |
| C2 | **仅 public 行情**；执行/持仓/资产整体排除。 |
| C3 | **首批交易所**：Binance + OKX（现货 + U本位永续）。扩容再加 Bitget / Hyperliquid。 |
| C4 | **通道**：1m K线 / 全市场成交 / ticker / L1(bid-ask) / 资金费（含 mark/index/funding/OI/清算）。orderbook 深度仅核心集（~10-20 标的），且一期可不做。 |
| C5 | **全标的主通道**（kline/ticker/trade 走批量/全市场单调用）；**orderbook 深度仅核心集**。 |

### 4.2 事件中心 (EventCenter)

| # | 决策 |
|---|---|
| E1 | 事件中心**独立**，抽象 `EventCenter` trait + 统一 envelope + **可插拔 backend**（**Kafka / Redis / Iggy / NATS** 四款支持）+ **多序列化格式（默认 JSON）**。 |
| E2 | 契约层（所有 backend 必须满足）：**at-least-once 投递 / 尽力有序 / 消费组（多消费者共享消费）**；**消费侧无 ack**（读取即推进位点，一致性靠幂等 `event_id` + 数据检查修复节点兜底，03 §4.4）。 |
| E3 | 能力层（`capabilities()`）：分区支持 / 重放（本端保留/时间范围重放）/ 死信 / 持久化保留策略。 |
| E4 | 不放进抽象 API：全局有序、事务性保证、后台重放、K/V 查找。 |
| E5 | **两级信封**：公共头只留跨家族字段（event_type/shard/event_id/received_ts/x_version/source），行情专属字段（venue/market/native_code/exchange_ts）下移进 `Body::Market`；`Body` 为 enum 分派。行情负载直接复用 dig3 的 `core::types::market_data`，不另造行情结构。 |

### 4.3 存储层

| # | 决策 |
|---|---|
| S1 | 存储层**抽象**，订阅事件中心 → 落盘/DB，后端可插拔（CK / duckdb / …）。 |
| S2 | 存储是「总线之后的服务」：正式消费方之一，与信号引擎并列。 |
| S3 | **回放源 = 存储层**（不依赖事件中心 backend 的重放能力，也不依赖 dig3 内部文件）。 |
| S4 | 数据服务查询统一读**存储层**（不是总线），避免「实时一个数、历史一个数」。 |

### 4.4 信号引擎

| # | 决策 |
|---|---|
| G1 | **声明式 RuleGraph（DAG）+ 内置算子库，无沙箱**。新增信号 = 配置组合现成算子；真溢出时加 Rust 算子。 |
| G2 | 信号引擎 = **独立进程**，订阅事件中心的行情/因子事件 → 算 → 把信号事件发回事件中心。 |
| G3 | **一等回放/回测**：同一份规则配置，实时源=总线，回放源=存储层（历史事件按序喂同一 DAG）。 |
| G4 | 信号事件**必须携带**：`signal_id`（稳定ID）/ `signal_name` / `version` / `instrument` / `direction`（多头/空头/中性）/ `value` / `timeframe` / `timestamp`；payload 放因子值明细（供告警条件引用）。 |
| G5 | 信号引擎消费「行情事件 + 因子事件」两路并列输入。 |

### 4.5 监控告警

| # | 决策 |
|---|---|
| O1 | 主职 = **对信号规则告警**：订阅信号事件 + 信号元数据，独立告警规则配置（B 模式），条件判定（AND/OR/阈值/时间窗/标的）→ 路由到渠道。 |
| O2 | 副职 = **平台性能监控**：各进程上报 `ops.*` 事件（心跳/延迟/断流/落后/畸形），告警引擎消费统计。 |
| O3 | **渠道后端可插拔**：飞书/钉钉（Webhook，免费）一期；电话/短信/邮件/自定义 Webhook 留 trait，二期。 |
| O4 | 告警规则独立配置；信号事件必须带信号元数据引用（signal_id/version/…），告警规则按 signal_id + 信号事件字段判定。 |

### 4.6 因子挖掘

| # | 决策 |
|---|---|
| F1 | 独立模块，与信号引擎**并列**（主走 B：通过事件中心间接耦合）。 |
| F2 | 二级事件生产者：订阅原始行情事件，产出**中间量事件（因子事件）**；信号引擎把因子事件当普通输入源，与行情事件并列。 |
| F3 | 因子挖掘不依赖信号引擎做任何事。 |

### 4.7 数据服务

| # | 决策 |
|---|---|
| D1 | **一等 SQL/文件导出**：直连存储层（CK/duckdb），消费方直接 SELECT；文件导出=按范围导出 CSV/Parquet。 |
| D2 | **二等鉴权 REST/WS 推迟**：REST 待定；**WS 砍掉（本期不做外部实时订阅）**。 |
| D3 | 查询统一读存储层。 |

### 4.8 控制面 / 元数据 / 部署

| # | 决策 |
|---|---|
| M1 | **控制面服务 = 配置事实来源**：信号/告警/因子规则、订阅计划、渠道配置、元数据集中存放。 |
| M2 | 事件中心只广播「配置已变更」通知；引擎从控制面**拉取自身配置**（热更新的事实来源，历史可查可回滚）。 |
| M3 | **部署形式不设计**（一分部署/编排内容都没有）。 |
| M4b | **目录类页面与币信息**（`docs/14`）：catalog **全量、不看名单**（名单只管采集）；交易对/币只读（同步为唯一写入方）、交易所可写；交易所同步 5 分钟、**币详情（链/合约/Twitter/发行流通）独立 1 小时节拍走 CoinGecko**，匹配三级（精确→转人工→可手填），股票类按 `exchange.asset_class` 跳过链上信息 |
| M4 | **定时任务**：控制面每 5 分钟从各所拉取交易对信息与币信息（公共端点、元数据配额份额），无变更不动作；变更触发指派重算，参考信息经 `md.meta` 事件落存储（09 §2.3）。 |

## 6. 四条红线

1. **抽象层 = 契约 + 能力表，不锁死后端**（事件中心/存储都如此；能力表阻止 Redis Streams 这类薄后端泄漏语义）。
2. **实时与回放/查询统一读同一个标准化源**（实时=总线，回放/查询=存储层；一致来源于此）。
3. **一切「配置」归控制面，引擎无本地配置事实**（改配置→广播→引擎拉取；部署与编排不设计）。
  八域全集、版本与发布流程、分片指派见 **09-控制面**。
4. **星型拓扑**：事件中心是唯一中枢，节点之间不直连（唯一例外 = 查询面直读存储后端）；
   加节点 = 加一个总线订阅方，不改任何已有节点。

### 8.2 体积优化（根 `Cargo.toml` 的 `[profile.*]`）

本盘 76G、其上并存 60+ 仓库，**构建产物曾反复把盘吃满**（单会话内清过 3 次增量缓存、1 次调试符号）。
三类体积元凶对应的三项配置：

| 配置 | 作用 | 代价 |
|---|---|---|
| `[profile.dev/test.package."*"] debug = false` | **依赖不要调试信息**——`deps` 体积最大头（dig3 / tokio / ed25519 那些符号），且不调试它们内部 | 依赖栈回溯无源码行 |
| `[profile.dev] debug = "line-tables-only"`<br>`[profile.test] debug = "line-tables-only"` | 自己代码保留**行号级**信息：`panic`/`assert` 的 `file:line` 不依赖 DWARF，栈回溯仍能定位源码行 | 比 full debug 小得多 |
| `[profile.dev] incremental = false` | **关闭增量缓存**——它每次再生 3.0~5.7G，是满盘主因 | 改单个 crate 需重编该 crate（不是全 workspace） |
| `[profile.release] strip = true` | 发布产物剥符号 | 仅影响 release |

**`debug-assertions` 不受影响**（dev/test 默认仍为 `true`）：采集与指派里用 `debug_assert!`
钉死的协议不变量（`x_version` 仅 K 线族、`shard == instrument_id`、`event_id` 跨格式一致等）
**依然生效**——这一点是刻意确认过的，别为了省体积关它。

**实测效果**（`cargo clean` 后全量重建）：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| `target/` 总计 | 10.4G | **1.5G**（−85%） |
| `target/debug/deps` | 6.9G | 1.4G |
| `target/debug/incremental` | 3.0~5.7G（再生） | **0** |
| `deps/*.pdb` | 3.8G / 109 个 | 332M / 37 个 |
| `cargo test --workspace` | 257 通过 | **257 通过（0 失败）** |

> 需要深度调试依赖内部（如 dig3 连接器、tokio 调度）时，临时把
> `profile.dev.package."*".debug` 改回 `true` 并 `cargo clean`，调试完再还原。

### 8.3 空间不足时的手动回收（按代价从小到大）

| 操作 | 典型回收 | 代价 |
|---|---|---|
| `rm -rf target/debug/incremental` | 3.0~5.7G | 下次增量失效（本配置已默认关闭，通常为空） |
| `rm -f target/debug/deps/*.pdb` | 数百 M~3.8G | 丢失调试符号，重建时重生成 |
| `rm -rf target/debug/examples` | ~300M | 示例二进制需重编 |
| **`cargo clean`** | 9~10G | 全量重编（约 15~30 分钟） |
| 清理其它仓库 `target/` | 视仓库而定 | 那些项目下次全量重编 |
