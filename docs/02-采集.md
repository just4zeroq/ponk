# 02 采集模块（采集 = digdigdig3）

> 对应 `01-architecture` §4.1（C1~C5）。本模块是平台与外部行情源的**唯一边界**：
> 一切行情数据从这里进入事件中心。连接器层**直接采用 digdigdig3**，本模块的职责 =
> 在 dig3 **连接器层**（ExchangeHub + REST/WS 连接器 + core 类型）之上做**平台适配**
> （订阅计划、采集进程生命周期、事件产出、断线自愈），而不是重新实现连接器。
> **不依赖 `digdigdig3-station`**（其代码已从依赖中删除）——station 原提供的自愈/落盘/warm-start
> 三项，前者由本模块自建（§6），后两者本就归存储层（04）。

---

## 1. 定位与边界

```
                    订阅计划(来自控制面 M2)
                           │
   dig3 ExchangeHub (连接器层)   ←─┐ 控制面下发
   (Binance/OKX spot+swap, 首期)  │
   │ 27 DataPoint / 能力表 /     │
   │ symbol规范化 / WsProtocol   │
   ▼
 采集进程(per (venue, market)?)   ── 进程模型见 §4
   │ 标准化事件 (envelope + dig3 类型payload)
   ▼
① 事件中心 EventCenter(抽象, backend可插拔)
```

- **采集不做业务**：不判断信号、不做存储、不自己决定告警。它只负责把行情事件可靠地送进事件中心。
- **采集不做发现**：采集哪些所、哪些市场、哪些标的、哪些通道，**全部由控制面下发的订阅计划决定**（M2；与既有 PONK 定案 C：instrument meta 随 config 下发一致）。
- **采集不碰私有数据**：仅 public 行情（C2）。

## 3. Symbol 规范化

dig3 自带 `SymbolNormalizer`（22 个 per-exchange 子模块：Binance `BTCUSDT`、OKX `BTC-USDT`…），且明确「normalization 在连接器之外，连接器只接受交易所原生字符串」。

**PONK 侧决策**：
- 平台内统一的 instrument canonical = **`venue:market:native_code`**（沿用既有 PONK 定案 C）。
- dig3 的 `Symbol{base, quote}` 作为跨所语义层；`SymbolNormalizer::to_exchange` 负责 canonical → 各所原生。
- 调用 dig3 一律用其 `SymbolInput`（raw 字符串或 canonical Symbol 均可）——**优先 canonical**，避免 each-call 转译。
- instrument meta（精度/小数位等）由控制面在订阅计划中下发（M2 + C）。

## 4. 采集进程模型（已定）

**进程是承载容器，不是分片单位**——一个采集进程可以承载**多个交易所**的交易对数据。

| 层 | 单位 | 谁决定 |
|---|---|---|
| **逻辑分片**（所有权/限频/配额单位） | `(venue, market, shard_idx)` | 控制面切分 |
| **进程**（承载容器） | 一个进程承载 N 个分片，**可跨所** | 控制面指派（分片 → 进程） |

- 解耦的收益：进程拓扑（几个进程、每进程装什么）成为部署自由度，**分片的语义不随部署变形**；
  一个进程带 binance-spot + binance-swap + okx-spot 完全允许。
- **配额仍是 venue 粒度**：`dig3 ExchangeHub` 是多所入口，进程内按 venue 各建自己的令牌桶 /
  `rateLimit`（配额域 = (venue, 出口IP)，01/既有 PONK 定案不变）——**所与所之间的配额互不串**。
- 进程内按 **shard × 通道** 开多个 dig3 通道（利用其批量方法 / 全市场单调用，连接数 ≈ 通道数）。
- ticker / L1：**共用同一条 WS Ticker 流，不分片**。⚠️ **原「全市场单调用」的假设不成立**（实测）：
  dig3 `MarketData` trait **没有 `get_tickers()` 批量接口**，WS `SubscriptionRequest` 也强制逐 symbol ⇒
  「全市场」实际退化为**逐标的订阅**，受 `max_instruments_per_round` 与配额约束。
  L1 仍是 ticker 副产品（不需要单独 orderbook 端点）。
- **`md.ticker` 与 `md.l1` 的关系（已定）**：同一帧**两个主题都发**——`md.ticker` 全字段、
  `md.l1` 只含 bid/ask/qty 的轻量派生视图。两者 `event_type` 不同 ⇒ `event_id` 不同，互不去重。
  不做成「配置了 l1 却只收到 ticker」的隐式行为；存储层可只落一份（l1 可由 ticker 派生）。
- kline / trade：按核心集 / 全市场分别订阅；冷门标的断流误判问题——沿用既有 PONK 的「触发用连接级信号，不靠单通道静默」决策。
- **catalog 与名单无关**：`instrument` / `asset` 是**全量目录**（`docs/14 §1`），不因黑白名单或节点 scope 被剔除；**名单只决定要不要订阅这条 `md.*`**。
- **标的集 = 控制面白名单**（采集不做发现）：`subscribe/diff` 只按白名单执行；交易所上新时
  **由控制面发现并推送给采集器**（命令信道，10 §4.2）。白名单之外的标的一律不采。
  发现机制 = 控制面**每 5 分钟**的交易对/币信息同步任务（09 §2.3）：拉 `get_exchange_info`
  与币信息 → 比对 catalog → 有变更才重算并下发，采集侧表现为期 `Diff`/`Snapshot`。
- **进程内不建行情缓存**（已定）：不做「最近 N 条」环形流水，也不维护 per-symbol 最后值槽。
  采集是**无状态转发者**——断流判定由 06 直接观测 `md.*` 流（06 §5）；K线回补起点用
  **固定回补窗口**（now − 固定时长）而非缓存状态（§6）。进程内只留**在线计数器**
  （发送积压、降级计数），不是缓存。

## 5. 事件产出（采集 → 事件中心）

- **envelope**（E5，两级信封）：公共头 = event_type / shard / event_id / received_ts / x_version / source；
  行情专属字段（venue / market / native_code / exchange_ts）在 `Body::Market` 内（03 §5.1）。
- **payload = dig3 类型**：`core::types::market_data` 直接复用（E5），不另造行情结构。
- **幂等键**：沿用既有 PONK 定案——`event_id = instrument_id:event_type:身份时间:内容哈希`；
  `candle_1m` 额外 `x_version = 采集接收时间`（Replacing 版本），避免「同 bar 内容即同 event_id、版本相同丢收盘」。
- 原始存储：采集只往事件中心发；**存储层**（04 模块）作为正式消费方订阅事件中心落盘（S1/S2）。

## 6. 降级 / 自愈 / 配额

- **静默检测 = 连接级**（每条连接一只时钟，非 per-channel、非 per-symbol），**仅用于触发重连**，
  **不产出任何静默告警**——断流告警由 06 观测 `md.*` 得出（06 §5）。这样与「采集不报静默」不冲突：
  重连是采集的自恢复，告警是监控的职责。
- **`Market` → dig3 `AccountType` 映射（已定）**：`spot → Spot`、**`swap → FuturesCross`**、**`future → FuturesCross`**（交割与永续同属合约类；`FuturesIsolated` 永不使用）
  （不是 `FuturesIsolated`——Binance/OKX 的 futures `TopicRegistry` 以 `FuturesCross` 为注册键，
  传 `FuturesIsolated` 匹配不到）。配置留 `account_type_overrides` 逃生口。
- **WS 断线处理：只重连，不回补**（已定）：
  1. 检测：连接级信号（WS `Err` / 静默超时按通道分类）；
  2. 恢复：重连 + `subscribe` 重放订阅集；
  3. **不做数据回补**——断档区间不补（K线留洞、trade/ticker 本就不可补）。
  断档的**发现、标记与修复**统一归未来**「数据检查与修复节点」**（01 §7）。
  station 原有的 auto-heal（回补）随 station 删除且**不重建**——回补是数据质量职责，不是采集职责。
  推论：采集侧**不实现任何 REST 回补路径**，配额份额里的"回填"角色（06 配额仲裁中的 35%）
  也随之指向未来的检查修复节点，不由采集进程持有。
- **REST 降级**：ticker/L1 可全市场 REST 降级；candle 仅核心集可降级，其余交回补；trade 不降级（沿用既有 PONK 决策）。
- **配额仲裁**：沿用既有 PONK——**进程内按 venue 各自的令牌桶**做配额仲裁（多所同进程时所间不串）；**控制面按 IP 切固定份额**（采集~50% / 回填~35% / **元数据~15%**）。⚠️ **执行靠进程内 per-venue 令牌桶，不是 dig3 `rateLimit`**——`RateLimitCapabilities`
  是纯声明式能力表、**无运行时执行器**（Binance/OKX 未接线），原「按份额配 dig3 rateLimit」不可执行；
  份额数值由控制面 `quota_share` 下发，桶按份额执行。其中「元数据」份额供**控制面的 5 分钟交易对/币信息同步任务**（09 §2.3）与元数据类任务使用，**不由采集进程持有**。不做运行时协调，先静态后动态。**「回填」份额不属于采集进程**（采集不回补），它留给未来的数据检查修复节点与元数据任务持有。
- **能力表**：dig3 `HasCapabilities`（validation snapshot 实测）作为「该所该通道能否用」的唯一事实来源（沿用 dig3 架构不变量），平台能力表是它的消费方之一。
- **进程承载上限 = 控制面配置项**（已定）：控制面配置「每进程最大分片数 / 最大标的数」，
  指派分片时按此约束（09 §2）。数值默认值待 dig3 连接器层内存实测后定，**但它是配置而非硬编码**——
  装不下就改配置、开更多进程。
- **失效域扩大（已知代价）**：一进程挂 → 它承载的**所有所**的数据同时断。缓解：
  ① 06 按通道从 `md.*` 判定具体是哪个所断（进程级心跳只判"进程没了"，见 06 §5）；
  ② 高可用诉求高时，控制面把同一所的分片**打散到多个进程**（分片→进程指派时的分布策略）。

## 7. 采集节点生命周期与控制面交互

一个采集实例的一生：**控制面登记 → 生成配置 → 启动注册 → 心跳 → 接收订阅信息 → 采集发送**。
采集器与平台之间只有三条信道（10 §2），**不直连控制面**（红线 4）。

### 7.1 全流程

| # | 阶段 | 谁发起 | 载体 / 动作 |
|---|---|---|---|
| ① | **节点登记** | 操作者（控制面） | 在控制面新建一个采集节点：**名称即唯一标识**（= `instance_id`），并声明它的期望范围（交易所、市场类型、数据类型、交易对集）与运行参数 |
| ② | **生成配置** | 控制面 | 导出该节点的配置文件（`instance_id` + 控制面地址 + 运行参数；**可带一份冷启动兜底计划**）。**只导出内容，不远程部署**（部署编排仍在范围外，01 M3） |
| ③ | **启动注册** | 采集进程 | `ops.collector.<instance>` ← `OpsHeartbeat{Startup, host, applied_version, counters}`。`host` 让控制面知道实例落在哪台机器（§7.3） |
| ④ | **心跳** | 采集进程 | 每 5s `Running` 心跳（`applied_version` + 在线计数器 + 承载能力）；控制面据此判存活与收敛（10 §5） |
| ⑤ | **接收订阅信息** | 控制面 → 采集 | 控制面把该实例的 `SubscribePlan` 经 `ctl.collector.<instance>` 下发（或采集经 `ctl.request.<instance>` 拉取）。**订阅信息四要素 = 交易所 / 市场类型 / 行情数据类型（通道）/ 交易对（含精度 meta）** |
| ⑥ | **启动采集** | 采集进程 | 版本门裁决 → **整包应用** → 建连接、按标的与通道订阅 → WS 帧转样本 |
| ⑦ | **发送到事件中心** | 采集进程 | `md.<channel>` ← `Body::Market`（信封与幂等键见 §5、03 §5） |

### 7.2 订阅信息的内容

控制面下发的订阅信息就是 `SubscribePlan`（03 §5.3），四要素一一对应：

| 你说的要素 | 字段 |
|---|---|
| 交易所 | `ShardPlan.venue` |
| 市场类型（现货 / 永续 / 交割） | `ShardPlan.market` |
| 行情数据类型 | `InstrumentMeta.channels`（`candle_1m` / `trade` / `ticker` / `l1` / `funding`，02 §2） |
| 交易对信息 | `InstrumentMeta.native_code` + `price_precision` / `qty_precision` / `meta` |

### 7.3 机器维度与分片

- **实例 → 机器**：采集进程在 register 心跳里上报 `host`；控制面维护映射，并按 `host` **分散分片**
  （同一台机器上不堆同一交易所的全部分片，降低单机故障影响面）。
- **分片由控制面切**：操作者只声明"这个实例采哪些所 / 哪些数据类型 / 哪些标的"；
  当范围超出单实例承载上限（09 §5.2）时，**控制面切分片并指派给多个实例**（09 §5）。
  采集侧不理解分片语义，只按收到的计划执行。
- **控制面不远程起进程**：配置由控制面生成，**部署动作归部署方**（systemd / 脚本 / 手工）。

### 7.4 同名注册（重登语义）

**同名 = 同一实例重登**（进程重启、迁移、扩容后顶替），不是新实例：

- 控制面**保留**该实例的历史 `assignment_version`，重登后**继续单调递增**下发——
  否则新进程会被自己的强序门（10 §4.3「旧版丢弃」）永久拒收；
- 重登时**清除**失联/停用状态，重新纳入候选集（控制面实现见 09 §6.2）；
- 旧进程若仍在跑，其心跳会被控制面视为同一实例的心跳（`host` 不同则记录并告警，
  由操作者处置，**不自动杀进程**）。
