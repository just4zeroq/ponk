# 10 信道规划（数据信道 / 命令信道 / 控制信道）

> 细化 `01-architecture` §3 与 `02-采集` / `09-控制面` 的通信面：采集模块与控制面、事件中心
> 之间共**三条信道**。核心判据 = 三类通信的 QoS 完全不同，混在一个主题族会让确认、顺序、
> 错误处理互相污染（数据不要求回执，命令要求版本收敛，控制要求可验证的存活观测与收敛）。

---

## 1. 三信道定义

| 信道 | 本质 | 方向 | 语义边界 |
|---|---|---|---|
| **数据信道** | 采集的**产物**（行情） | 采集 → 事件中心 → N 消费方 | 单向广播、无回执 |
| **命令信道** | 控制面的**意图**（该采什么） | 控制面 → 单个采集实例 | 定向、版本强序、必须收敛 |
| **控制信道** | 采集的**事实**（活着吗、应用到哪版） | 采集 → 总线 → 控制面 | 周期/事件式、消费组读 + 快照键兜底 |

判据一句话：**意图要收敛（命令），事实要观测（控制），产物要分发（数据）。**

## 2. 总览

| # | 信道 | 载体 | 频率 | 投递 | 顺序 | 确认 | 消费者/发送者 |
|---|---|---|---|---|---|---|---|
| D | 数据信道 | 事件中心 `md.*` | 高（每秒数百~数千） | at-least-once | 同 (topic, shard) 尽力有序 | **无回执** | 04 存储 / 05 信号 / 07 因子 |
| C | 命令信道 | 事件中心 `ctl.collector.<instance>`（推）+ `ctl.request.<instance>`（拉） | 低（配置变更时） | at-least-once + 拉取兜底 | **版本强序**（`assignment_version` 单调） | 心跳 `applied_version` 隐式 ACK | 单个采集实例 |
| H | 控制信道 | 事件中心 `ops.collector.<instance>` + `ctl.request.<instance>` | 心跳 5s | at-least-once + **兜底快照键** | n/a | 快照键恢复 + 版本收敛 | 控制面（消费组）；06 订阅同一主题 |

> 全平台**单一传输 = 事件中心**（已定）：三信道只在**主题族、QoS、消费方式**上区分，不换传输。

## 3. 数据信道

- **主题**（03 §8）：`md.candle.1m` / `md.trade` / `md.ticker` / `md.l1` / `md.funding`（+ OI/清算等二期）
- **分片键**：`Envelope::shard` 字段（行情/信号/因子 = `instrument_id` 稳定哈希；心跳/告警/配置 = `None` → 默认分区）
- **envelope**：03 §5.1（公共头 event_type / shard / event_id / received_ts / x_version / source + `Body::Market`{venue / market / native_code / exchange_ts}）
- **投递语义**：at-least-once + 消费组；**采集不等任何消费方回执**（不回压、不阻塞）
- **背压**：**不做**（已定：`01` §待定项外的显式决定）——积压由 **06 监控观测**（ops.lag），由人处置
- **错误**：发送失败重试，最终失败进 `dlq.md.*`（03 §7.3）
- **广播性质**：一份数据、N 个消费组，各消费组各自推进（存储/信号/因子互不干扰）

## 4. 命令信道

> **消息结构集中定义在事件中心协议层**（`SubscribePlan` / `ConfigChanged`，03 §5.3）；
> 本节只讲**信道语义**：谁发、何时发、顺序、确认与收敛。


### 4.1 双路径（推 + 拉）

```
控制面 ──推──► ctl.collector.<instance>   (低延迟通知/定向)
控制面 ◄──拉── 采集 (ctl.request.<instance>，携带 applied_version)
```

- **推**：变更时定向推送给 `ctl.collector.<instance_id>`（控制面不需要知道采集的网络地址，
  靠主题寻址）。
- **拉**：采集启动时、或心跳发现 `applied_version` 不收敛时，在 `ctl.request.<instance>`
  发一条携带 `applied_version` 的请求；**控制面用命令信道的 snapshot 命令作答**（不需要单独
  的 response 主题——snapshot 本来就是命令）。
  **拉是正确性保证，推只是加速**——总线消息丢失/新建消费组读不到历史时靠拉兜底（替代
  backend 的 replay 能力，与 03 §7.2 一致）。

### 4.2 命令内容

| 命令 | 内容 |
|---|---|
| 订阅计划 snapshot | venue/market/标的集/通道 + instrument meta（精度）+ 黑名单 |
| 订阅计划 diff | 增量加/减标的、通道变更、黑名单变更 |
| 配额份额 | 按 (venue, 出口 IP) 的静态份额（采集 ~50%） |

### 4.3 语义：状态补丁，不是动作流

- 每条命令带递增 **`assignment_version`**；
- 采集收到**旧版本 → 直接丢弃**，收到**新版本 → 整包应用**（幂等键 = 版本号）；
- 采集**不需对每条命令回 ACK**：心跳里的 `applied_version` 就是隐式确认（02 §7 / 06 §5）；
- 控制面判收敛 = `applied_version == assignment_version`；N 秒不收敛 → 重推 + 06 告警。
  **不做**配置应用失败反馈与回滚（已明确排除，09 §1）。

## 5. 控制信道（走总线，已定）

> 消息结构集中定义在事件中心协议层（`OpsHeartbeat`，03 §5.3）；本节只讲发送时机与频率。


| 信号 | 时机 | 内容 | 主题 |
|---|---|---|---|
| **register**（启动注册） | 一次 | instance_id / **承载能力（可装哪些所/多少分片）** / 启动时间；控制面收到后在命令信道回**初始订阅计划 snapshot**（= 指派给本进程的分片集，可含多所，省一次拉取） | `ops.collector.<instance>` |
| **heartbeat** | 每 5s | `applied_version` + 在线计数器：发送积压、降级计数（**不报静默**——静默由 06 观测 `md.*` 得出，06 §5） | `ops.collector.<instance>` |
| **shutdown** | 一次 | 正常下线（缺失 → 失联判定） | `ops.collector.<instance>` |
| **pull snapshot** | 启动 / 版本不收敛 | 携带 `applied_version` 的请求，控制面用命令信道 snapshot 作答 | `ctl.request.<instance>` → 命令信道 |

- **单一传输**：控制面作为 `ops.collector` 的消费组消费状态；06 监控订阅**同一主题**（同一面，
  不需要 fan-out，控制面不代发）。
- **兜底快照键**：存放于**控制面自身状态存储**（事件中心不提供 K/V，03 §3），06 不读它。
  控制面消费心跳后，把「每实例最新状态」写入快照键；
  控制面重启 / 消费组重建时从快照键恢复，避免「历史心跳已过期 → 状态空洞」。
- **失联判定**：`shutdown` 缺失 + 心跳断 3×5s → 判死（既有 PONK 定案；再平衡防抖已排除）。
- **已知代价（接受）**：**总线整体故障时，控制面会把「总线死」误判成「全部采集死」**。
  缓解 = 06 同时监控总线自身健康（backend 连接 / Lag 指标），靠它区分两类故障；且失联
  **只产生告警、不触发任何自动动作**（再平衡已排除），误判成本低。
- **收益**：全平台单一传输；控制面与监控同订阅面；控制面无需维护入站连接。

## 6. 职责映射（五件通信 → 信道）

| 通信事项 | 信道 |
|---|---|
| 采集器**启动注册** | **控制信道**（register 发 `ops.collector.<instance>`；控制面经**命令信道**回初始 snapshot） |
| 控制面**下发交易对**（订阅计划） | **命令信道**（snapshot/diff，版本强序） |
| 采集器**心跳** | **控制信道**（heartbeat 5s，带 applied_version） |
| 控制面**下发命令**（配额/配置变更） | **命令信道**（`ctl.collector.<instance>` 推 + `ctl.request.<instance>` 拉兜底） |
| 采集器**数据广播** | **数据信道**（md.* → 事件中心 → 消费组） |

## 7. 启动时序

```
采集进程启动
  → ops.collector.<instance>(register, applied_version=0)     (控制信道, 上行)
  → ctl.request.<instance>(pull, applied_version=0)           (控制信道 → 命令信道, 拉)
  ← ctl.collector.<instance>(snapshot, assignment_version=N)  (命令信道, 下行)
  → 应用订阅计划 (applied_version=N)
  → 订阅 md.* → 开始发数据 ────────────► 事件中心              (数据信道)
  → heartbeat(applied_version=N) 每 5s ─► 事件中心             (控制信道)
  → 控制面写兜底快照键(实例状态) → 06 也能读到 ops.collector

  (变更时)
  控制面 ──ctl.collector.<instance> version=N+1──► 采集        (命令信道, 推)
       或 采集心跳发现 applied_version≠N → ctl.request 拉        (命令信道, 拉)
  → 采集应用 → 心跳 applied_version=N+1 → 控制面比对收敛 → 更新快照键

  (下线)
  采集 → ops.collector.<instance>(shutdown) → 控制面判下线
  (异常下线无 shutdown → 3×5s 无心跳 → 判死 + 06 告警)
```

## 8. 明确排除

- 再平衡防抖 / 配置应用失败反馈 / 回滚（09 §1 已排除）
- **背压处理**（数据信道不做，交 06 监控观测）
- pause / resume / kill 类管理指令
- **gap 缺口登记**（不在采集侧做，也不占信道）——移交给未来新增的**「数据检查与修复节点」**（见 01 §7 待定项），由它事后检测断档并修复/标记。心跳只保留通道静默等在线指标
- backend replay 作为命令送达保证（由拉取兜底替代）
